React ↔ REST API

Як React взаємодіє з backend

REST API — основи

REST (Representational State Transfer) — стиль організації веб-API навколо ресурсів та стандартних HTTP-механізмів. Основні ідеї:

  • Stateless — сервер не покладається на стан попередніх запитів; кожен запит має містити потрібний контекст;
  • Resource-oriented — URL ідентифікує ресурс (/api/users, /api/products/42);
  • HTTP-методи визначають операцію: GET (read), POST (create), PUT/PATCH (update), DELETE (delete);
  • Формат даних — зазвичай JSON;
  • HTTP status codes — 200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 404 Not Found, 500 Server Error.

React не має вбудованого API-клієнта — використовується fetch() або сторонні бібліотеки (Axios, ky).

Де живе API-логіка в React

У невеликому компоненті прямий fetch() можливий. Але коли API використовується в кількох місцях, краще винести HTTP-логіку окремо, щоб UI не залежав від деталей запиту:

  1. API Layer (api/client.ts, api/users.ts) — HTTP-клієнт, endpoint-функції, типи запитів/відповідей;
  2. Custom Hooks (hooks/useUsers.ts) — управління станом запиту (loading/error/data), виклик API Layer;
  3. Components — лише споживають дані з hooks, відображають UI.

Компонент може знати про useUsers(), а hook — про API layer. Так UI не залежить від URL, headers та деталей HTTP-запиту.

Перший запит: fetch()

import { useState, useEffect } from "react";

type User = { id: number; name: string };

function UserList() {
  const [users, setUsers] =
    useState<User[]>([]);

  useEffect(() => {
    fetch("https://api.example.com/users")
      .then(r => {
        if (!r.ok)
          throw new Error("Failed");
        return r.json() as Promise<User[]>;
      })
      .then(setUsers)
      .catch(err => console.error(err));
  }, []);

  return (
    <ul>
      {users.map(u => (
        <li key={u.id}>{u.name}</li>
      ))}
    </ul>
  );
}

fetch() — нативний браузерний API.

Особливості fetch:

  • не кидає error на 4xx/5xx — треба перевіряти res.ok;
  • потрібен ручний .json() парсинг;
  • повертає Promise (then/catch або await);
  • підтримує AbortController для скасування.

Мінус: багатослівний — для кожного запиту треба писати перевірки, headers, error handling.

Навчальний контекст: тут показуємо базовий client-side flow. У production часто використовують framework data APIs або query library, щоб не будувати cache/refetch/invalidation вручну.

→ тому використовують Axios або API Layer-абстракції.

Асинхронні стани

Стан запиту: idle → loading → success / error

Чому потрібен status-стан?

Для простого запиту зручно розрізняти чотири стани:

  • idle — запит ще не запускався;
  • loading — запит триває, показуємо spinner / skeleton;
  • success — дані отримано, показуємо контент або Empty State;
  • error — запит не вдався, показуємо повідомлення + retry.

Проблема лише з isLoading: boolean не описує, чому даних немає. «Ще не завантажували», «список порожній» і «запит завершився помилкою» — різні ситуації.

Правильно: окремо status + data + error, або об'єднати в один стан через useReducer.

Pattern: "idle" | "loading" | "success" | "error" — один status описує фазу запиту, а data та error містять його результат.

Обробка станів — приклад з useReducer

type State<T> = {
  status: "idle" | "loading"
        | "success" | "error";
  data: T | null;
  error: string | null;
};

type Action<T> =
  | { type: "start" }
  | { type: "success"; data: T }
  | { type: "error"; error: string };

function reducer<T>(
  state: State<T>,
  action: Action<T>
): State<T> {
  switch (action.type) {
    case "start":
      return { status: "loading", data: null, error: null };
    case "success":
      return { status: "success", data: action.data, error: null };
    case "error":
      return { status: "error", data: null, error: action.error };
  }
}
// Custom Hook з useReducer
export function useAsync<T>(fn: () => Promise<T>, deps: DependencyList = []) {
  const [state, dispatch] =
    useReducer(reducer<T>, {
      status: "idle", data: null, error: null
    });

  useEffect(() => {
    let cancelled = false;
    dispatch({ type: "start" });

    fn()
      .then(data => {
        if (!cancelled)
          dispatch({ type: "success", data });
      })
      .catch(err => {
        if (!cancelled)
          dispatch({ type: "error", error: err.message });
      });

    return () => { cancelled = true; };
  }, deps);

  return state;
}

UI-патерни для асинхронних станів

function UserList() {
  const { status, data, error } =
    useAsync(() => api.getUsers(), []);

  if (status === "loading")
    return <Spinner />;

  if (status === "error")
    return (
      <ErrorView
        message={error}
        onRetry={refetch}
      />
    );

  if (status === "success" && data.length === 0)
    return <EmptyState />;

  return (
    <ul>
      {data.map(u => (
        <li key={u.id}>{u.name}</li>
      ))}
    </ul>
  );
}

Шаблони UI для станів:

  • Spinner — простий індикатор завантаження;
  • Skeleton — «каркас» майбутнього контенту;
  • Error view — повідомження + кнопка retry;
  • Empty state — «поки що немає даних»;
  • Error boundary — на рівні дерева (React 16+);
  • Toast / notification — для помилок мутацій.

Важливо: показувати користувачу не просто «Error», а зрозуміле повідомлення + спосіб виправити (retry, перевірити з'єднання).

Error Boundaries — межа ізоляції помилок UI

import { Component, type ErrorInfo, type ReactNode } from "react";

type Props = { fallback: ReactNode; children: ReactNode };
type State = { hasError: boolean };

class ErrorBoundary extends Component {
  state: State = { hasError: false };

  static getDerivedStateFromError(): State {
    return { hasError: true };
  }

  componentDidCatch(error: Error, info: ErrorInfo) {
    console.error(error, info);
    // logging / monitoring...
  }

  render() {
    if (this.state.hasError)
      return this.props.fallback;
    return this.props.children;
  }
}

// Використання
<ErrorBoundary fallback={<ErrorView />}>
  <UserList />
</ErrorBoundary>

Error Boundary — компонент, який показує fallback, якщо під час render виникла помилка в дочірньому React-дереві.

Ловить: помилки під час render у дочірньому React-дереві.

НЕ ловить: помилки в event handlers, асинхронних callback, setTimeout та коді поза React — там потрібні власні try/catch.

Важливо: Error Boundary не є аналогом try/catch для звичайного JavaScript-коду.

У React Error Boundary реалізують через class-компонент; для зручнішого API можна використати react-error-boundary.

Їх ставлять навколо частини UI: якщо дочірній компонент впаде, boundary покаже fallback, а інші незалежні частини інтерфейсу можуть продовжити працювати.

CRUD App — архітектура

Read — список + детальна сторінка

// hooks/useUsers.ts
export function useUsers() {
  const [state, setState] = useState<
    { users: User[]; loading: boolean; error: string | null }
  >({ users: [], loading: true, error: null });

  const refetch = useCallback(async () => {
    setState(s => ({ ...s, loading: true, error: null }));
    try {
      const users = await api.getUsers();
      setState({ users, loading: false, error: null });
    } catch (e) {
      setState({ users: [], loading: false, error: (e as Error).message });
    }
  }, []);

  useEffect(() => { refetch(); }, [refetch]);

  return { ...state, refetch };
}
// Використання
function UserListPage() {
  const { users, loading, error, refetch } =
    useUsers();

  if (loading) return <Spinner />;
  if (error) return (
    <ErrorView msg={error}
      onRetry={refetch} />
  );

  return (
    <ul>
      {users.map(u => (
        <li key={u.id}>
          {u.name}
          <Link to={`/users/${u.id}`}>View</Link>
        </li>
      ))}
    </ul>
  );
}

Create — додавання через форму

function CreateUserForm() {
  const [name, setName] = useState("");
  const [email, setEmail] = useState("");
  const [saving, setSaving] = useState(false);
  const [error, setError] = useState(null);

  const handleSubmit = async (e: FormEvent) => {
    e.preventDefault();
    setSaving(true);
    setError(null);
    try {
      await api.createUser({ name, email });
      // redirect або refetch list
      navigate("/users");
    } catch (err) {
      setError((err as Error).message);
    } finally {
      setSaving(false);
    }
  };

  return (
    <form onSubmit={handleSubmit}>
      <input value={name} onChange={...} />
      <input value={email} onChange={...} />
      <button disabled={saving}>
        {saving ? "Saving..." : "Create"}
      </button>
      {error && <p className="error">{error}</p>}
    </form>
  );
}

Стани форми Create:

  • idle — форма порожня, кнопка активна;
  • saving — запит триває, кнопка disabled, текст «Saving...»;
  • success — редирект на список або детальну;
  • error — показуємо помилку, форма залишається.

Після успішного створення:

  • редирект на список (navigate);
  • або refetch списку;
  • або додати в локальний state (optimistic).

Update — редагування існуючого

function EditUserPage({ id }: { id: string }) {
  const { data: user, loading } =
    useAsync(() => api.getUser(id), [id]);

  const [form, setForm] = useState(null);
  const [saving, setSaving] = useState(false);

  // Заповнити форму коли дані завантажено
  useEffect(() => {
    if (user) setForm(user);
  }, [user]);

  const handleSave = async () => {
    setSaving(true);
    try {
      await api.updateUser(id, form);
      navigate(`/users/${id}`);
    } finally {
      setSaving(false);
    }
  };

  if (loading) return <Spinner />;
  if (!form) return null;
  return <UserForm value={form}
    onChange={setForm}
    onSubmit={handleSave}
    saving={saving} />;
}

Особливості Update:

  • Спочатку завантажити поточні дані (GET /:id);
  • Заповнити форму початковими значеннями;
  • На submit → PUT/PATCH з оновленими даними;
  • Після успіху → редирект або оновлення;
  • PATCH — часткове оновлення (лише змінені поля);
  • PUT — повне заміщення ресурсу.

Важливо: не копіювати prop у state напряму (anti-pattern). Використовувати key={id} для скидання форми при зміні id, або controlled form.

Delete — з підтвердженням

function DeleteButton({ id, onDeleted }: {
  id: string;
  onDeleted: () => void;
}) {
  const [deleting, setDeleting] = useState(false);

  const handleDelete = async () => {
    if (!confirm("Delete this user?")) return;
    setDeleting(true);
    try {
      await api.deleteUser(id);
      onDeleted(); // refetch або navigate
    } catch (e) {
      alert("Failed to delete");
    } finally {
      setDeleting(false);
    }
  };

  return (
    <button onClick={handleDelete}
      disabled={deleting}>
      {deleting ? "Deleting..." : "Delete"}
    </button>
  );
}

Особливості Delete:

  • Підтвердження — confirm() або модальне вікно (небезпечна операція);
  • Кнопка disabled під час запиту;
  • Після успіху:
    • refetch() списку, або
    • видалити з локального state, або
    • редирект на список;
  • Обробка помилок → toast/notification.

Підтвердження можна замінити на модальне вікно з текстом «Are you sure?» + кнопки Yes/No.

AbortController — скасування запитів

// ❌ Без скасування (race condition)
useEffect(() => {
  fetch(`/api?q=${query}`)
    .then(setData)
}, [query])
// старий запит може перезаписати новий
// ✅ З AbortController
useEffect(() => {
  const ctrl = new AbortController();
  fetch(url, { signal: ctrl.signal })
    .then(r => r.json())
    .then(setData)
    .catch(err => {
      if (err.name !== "AbortError") setError(err);
    });
  return () => ctrl.abort();
}, [query]);

Axios варіант:

useEffect(() => {
  const ctrl = new AbortController()
  axios.get("/api/users", { signal: ctrl.signal })
    .then(res => setUsers(res.data))
    .catch(err => { if (!axios.isCancel(err)) setError(err) })
  return () => ctrl.abort()
}, [])

Оптимістичні оновлення (Optimistic UI)

Песимістичний (звичайний)

  1. User clicks "Delete"
  2. Show spinner
  3. Wait for server response...
  4. Remove item from list

UI затримується на час запиту.

Оптимістичний (швидкий UX)

  1. User clicks "Delete"
  2. Remove item from list INSTANTLY
  3. Send request in background
  4. If error → rollback (restore item)

UI миттєво реагує; при помилці потрібен rollback або повторна синхронізація.

У React 19 є useOptimistic для optimistic UI у межах Action; тут спочатку розбираємо базовий flow вручну. 

const deleteOptimistic = async (id: string) => {
  const prev = items;                    // 1. save snapshot
  setItems(items.filter(i => i.id !== id)); // 2. update UI now
  try { await api.deleteUser(id); }       // 3. send request
  catch (e) { setItems(prev); showError(); } // 4. rollback on error
}

Коли використовувати оптимістичні оновлення?

Підходить:

  • Delete — видалення зі списку (миттєво зникає);
  • Toggle (like / favorite) — швидка взаємодія;
  • Drag-and-drop reorder — порядок змінюється одразу;
  • Checkbox в таблиці — позначити виконано.

Сервер зазвичай підтверджує без помилок → користувач не чекає.

Не підходить:

  • Create зі складною серверною відповіддю — потрібен rollback / temporary id;
  • Платежі, транзакції та критичні операції — потрібне підтвердження;
  • Form submit зі складною валідацією;
  • Операції, де rollback складний або небезпечний.

Тут зазвичай обирають песимістичний підхід або обережний optimistic flow з надійним rollback.

API Layer та Axios

fetch vs Axios — порівняння

Axios — налаштування instance

// api/client.ts
import axios from "axios";

export const apiClient = axios.create({
  baseURL: "https://api.example.com",
  timeout: 10000,
  headers: {
    "Content-Type": "application/json",
    "Accept": "application/json",
  },
});

// Використання
const res = await apiClient.get("/users");
// res.data     → JSON-відповідь (авто-parsed)
// res.status   → 200
// res.headers  → response headers

// POST
await apiClient.post("/users", body);
// PUT
await apiClient.put(`/users/${id}`, body);
// DELETE
await apiClient.delete(`/users/${id}`);

Переваги Axios instance:

  • baseURL — не повторюємо домен;
  • timeout — запит не «висить» вічно;
  • headers — за замовчуванням для всіх запитів;
  • Авто JSON — не треба .json();
  • за замовчуванням reject для HTTP-відповідей поза 2xx;
  • Можна створити кілька instance (API v1, v2, third-party).

Встановлення: npm install axios

Axios Interceptors — глобальна обробка

Axios Interceptors — приклад

// api/client.ts — interceptors
import axios from "axios";

export const apiClient = axios.create({ baseURL: "https://api.example.com" });

// Request interceptor — додаємо auth token
apiClient.interceptors.request.use((config) => {
  const token = getAccessToken();
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});

// Response interceptor — обробка помилок
apiClient.interceptors.response.use(
  (response) => response, // success — пропускаємо
  (error) => {
    if (error.response?.status === 401) {
      // token expired → redirect to login
      clearSession();
      window.location.href = "/login";
    }
    if (error.response?.status >= 500) {
      // server error → show toast
      showToast("Server error. Try later.");
    }
    return Promise.reject(error);
  }
);

Interceptors — глобальні «фільтри» для всіх запитів/відповідей. Призначення: auth headers, error handling, logging, retry, metrics.

API Layer — endpoint-функції

// types/api.ts
export type User = {
  id: string;
  name: string;
  email: string;
};

export type CreateUserDTO = {
  name: string;
  email: string;
};

// api/users.ts
import { apiClient } from "./client";
import type { User, CreateUserDTO } from "../types/api";

export const usersApi = {
  list: () =>
    apiClient.get<User[]>("/users").then(r => r.data),

  getById: (id: string) =>
    apiClient.get<User>(`/users/${id}`).then(r => r.data),

  create: (data: CreateUserDTO) =>
    apiClient.post<User>("/users", data).then(r => r.data),

  update: (id: string, data: Partial<CreateUserDTO>) =>
    apiClient.put<User>(`/users/${id}`, data).then(r => r.data),

  delete: (id: string) =>
    apiClient.delete(`/users/${id}`),
};

Переваги endpoint-функцій:

  • Один джерело правди для всіх API-викликів;
  • Типізовані запити та відповіді (TS-дженерики);
  • Легко знайти всі місця використання endpoint;
  • Можна підмінити реалізацію (mock, test);
  • DTO-типи окремо від entity-типів.

DTO (Data Transfer Object) — тип для передачі даних у API-виклик (напр. CreateUserDTO без id).

У hooks викликаємо usersApi.list(), а не apiClient.get(...) напряму.

Repository — коли API-модель не збігається з UI-моделлю

// API DTO
type ApiTodo = {
  id: number;
  todo: string;
  completed: boolean;
  userId: number;
};

// UI/domain model
type Task = {
  id: string;
  title: string;

// Repository hides API details
const taskRepository = {

Repository — додатковий шар між API та доменною моделлю.

Він корисний, коли формат API відрізняється від моделі, яку використовує UI.

Для простого CRUD окремий Repository не є обов'язковим; у Лабораторній №10 він використовується саме для такого розділення відповідальностей.

Типові помилки при роботі з API

  • API-виклики в компонентах — замість API Layer. Ознака: компонент імпортує axios напряму → винести в api/;
  • Без cleanup в useEffect — старий запит може завершитися після нового. Рішення: AbortController і/або перевірка актуальності результату;
  • Без обробки error — fetch().then() без .catch. Користувач не бачить, що щось зламалось;
  • Дублювання baseURL — в кожному виклику "https://api...". Рішення: axios instance з baseURL;
  • Без типізації відповідей — any замість дженериків. Рішення: apiClient.get<User[]>();
  • Забули refetch після мутації — список не оновлюється після create/update/delete.

Server state vs Client state

Server state (дані з API):

  • асинхронний (fetch);
  • має caching, invalidation;
  • може бути stale (застарілим);
  • кілька компонентів можуть використовувати ті ж дані;
  • потрібен retry, refetch, optimistic.

→ TanStack Query, SWR (Лекція 15)

Client state (UI state):

  • синхронний;
  • короткочасний (form, toggle);
  • належить компоненту;
  • не потребує invalidation;
  • зникає при unmount / reload.

→ useState, useReducer, Context

На цьому етапі ми керуємо server state вручну (useEffect + fetch + useState). В Лекції 15 розглянемо TanStack Query — інструмент, що автоматизує caching, refetch, invalidation, optimistic updates.

Підсумок

  • React взаємодіє з backend через HTTP-запити (fetch/axios) — немає вбудованого API-клієнта.
  • Асинхронні стани — loading / success / error (status enum), не просто boolean. UI: spinner, error view, empty state.
  • CRUD = Create (POST), Read (GET), Update (PUT/PATCH), Delete (DELETE). Кожна операція — окремий UI-флоу з own states.
  • API Layer: api/client.ts (instance) → api/users.ts (endpoints) → hooks/useUsers.ts (state) → components/ (UI).
  • Axios — зручний HTTP-клієнт із instance, interceptors, timeout та автообробкою JSON. Це альтернатива fetch, а не обов'язково «кращий» варіант.
  • Interceptors — глобальна обробка: auth token, 401 redirect, error toast.
  • AbortController — дозволяє скасувати fetch під час cleanup; для stale response важливий також контроль актуальності результату.
  • Оптимістичні оновлення — миттєвий UI для швидких операцій (delete, toggle).
