SPA та маршрутизація

SPA vs MPA — навігація

Що таке SPA-маршрутизація?

SPA (Single-Page Application) — застосунок завантажується один раз, далі навігація відбувається без перезавантаження сторінки.

Маршрутизація (routing) — механізм, що зіставляє URL-адресу з відповідним компонентом для відображення.

Як це працює:

  • Клік по посиланню перехоплюється JavaScript;
  • URL оновлюється через History API (pushState);
  • React визначає, який компонент відповідає URL;
  • Рендерить його — без перезавантаження сторінки.

React не має вбудованого роутера. Для маршрутизації можна використовувати React Router або routing, який надає React framework.

Навіщо роутинг у SPA?

  • Bookmarkable URLs — користувач може зберегти посилання на конкретну сторінку;
  • Shareable — відправити посилання колезі, він побачить те саме;
  • Back/Forward — кнопки браузера працюють природньо;
  • SEO — окремі URL допомагають адресувати сторінки; для SEO важливі також SSR/SSG/prerendering та коректний HTML-контент;
  • Організація коду — розділення застосунку на логічні сторінки;
  • Code splitting — завантаження коду сторінки on-demand (lazy loading);
  • Аналітика — відстеження переглядів сторінок (pageviews).

URL як джерело стану

// ❌ State в компоненті
const [page, setPage] = useState(1);
const [filter, setFilter] = useState("all");
const [tab, setTab] = useState("details");

// втрачається при reload, не ділиться
// ✅ State в URL (router)
/products?page=2&filter=active
/users/42?tab=details

// shareable, bookmarkable, survives reload

Коли URL добре підходить для state:

  • Bookmarkable — можна зберегти посилання з точним станом;
  • Shareable — відправити колезі, він побачить те ж;
  • Back/Forward кнопки браузера працюють природньо;
  • Survives reload — стан не втрачається.

React Router — компонентна модель

React Router — базові компоненти

React Router — маршрутизатор для React з кількома режимами.

  • Declarative — базове зіставлення URL та UI;
  • Data — routes, loaders/actions та стани навігації;
  • Framework — route modules, data loading, code splitting та інші можливості.
  • <BrowserRouter> — обгортає застосунок, використовує HTML5 History API;
  • <Routes> — контейнер для списку маршрутів;
  • <Route> — зіставляє URL-шлях з компонентом;
  • <Link> — посилання без перезавантаження (renders <a>);
  • <Outlet> — місце, де рендеряться дочірні маршрути (nested);
  • <Navigate> — програмний редирект.

Встановлення: npm install react-router

React Router v8 — актуальна major-версія станом на 2026.

У Data mode RouterProvider імпортується з react-router/dom.

У цьому курсі починаємо з Declarative mode, а Data/Framework mode розглянемо як наступний рівень.

React Router — базова конфігурація

// JSX-стиль (декларативний)
import { BrowserRouter, Routes, Route, Link }
  from "react-router";

function App() {
  return (
    <BrowserRouter>
      <nav>
        <Link to="/">Home</Link>
        <Link to="/users">Users</Link>
      </nav>
      <Routes>
        <Route path="/" element={<Home />} />
        <Route path="/users" element={<UserList />} />
        <Route path="*" element={<NotFound />} />
      </Routes>
    </BrowserRouter>
  );
}

Складна навігація

Route Parameters — динамічні шляхи

// Конфігурація маршруту з параметром
<Route path="/users/:id"
  element={<UserDetail />} />

// Отримання параметра в компоненті
import { useParams } from "react-router";

function UserDetail() {
  const { id } = useParams();
  // URL: /users/42  →  id = "42"

  const { data, loading } =
    useUser(id);

  if (loading) return <Spinner />;
  return <div>{data.name}</div>;
}

Route params — динамічні сегменти URL, що стають доступні через useParams().

Синтаксис: :paramName в шляху.

Приклади:

  • /users/:id → /users/42
  • /posts/:slug → /posts/hello-world
  • /products/:category/:id → /products/electronics/5

Optional segments — до сегмента можна додати ?:

/posts/:id? → /posts, /posts/42

Query Parameters — useSearchParams

import { useSearchParams } from "react-router";

function ProductList() {
  const [params, setParams] =
    useSearchParams();

  const page = parseInt(params.get("page") ?? "1");
  const filter = params.get("filter") ?? "all";

  const goToPage = (p: number) => {
    setParams({ page: String(p), filter });
  };

  // URL: /products?page=3&filter=active
  return (
    <>
      <Filter value={filter} />
      <List page={page} />
      <Pagination current={page} onPageChange={goToPage} />
    </>
  );
}

Query params — параметри після ? в URL.

Призначення:

  • pagination (?page=3);
  • filtering (?category=books);
  • sorting (?sort=price);
  • search (?q=react);
  • utm-мітки для аналітики.

useSearchParams повертає URLSearchParams-об'єкт + setter.

Зміна query → URL оновлюється, компонент перерендериться.

Перевага: стан фільтра в URL — bookmarkable + shareable.

Nested Routes та Layouts

Nested Routes — Declarative та Data mode

Declarative mode — дерево маршрутів описуємо через JSX.

<Routes>
  <Route path="/dashboard" element={<Dashboard />}>
    <Route index element={<DashboardHome />} />
    <Route path="settings"
      element={<Settings />} />
    <Route path="profile"
      element={<Profile />} />
  </Route>
</Routes>

Data mode — те саме дерево задаємо як route objects.

const router = createBrowserRouter([
  {
    path: "/dashboard",
    Component: Dashboard,
    children: [
      { index: true, Component: DashboardHome },
      { path: "settings", Component: Settings },
      { path: "profile", Component: Profile }
    ]
  }
]);

<RouterProvider router={router} />

В обох підходах дочірній маршрут рендериться через <Outlet /> у батьківському компоненті. У Data mode до маршруту можна додати loader, action, стани навігації та інші Data APIs.

Nested Routes — глибше вкладення

// Declarative
<Route path="/dashboard" element={<DashboardLayout />}>
  <Route path="users" element={<UsersLayout />}>
    <Route path=":id" element={<UserDetail />} />
  </Route>
</Route>

// Data mode → children: [ ... ]

В обох підходах дочірній route рендериться через <Outlet />.

Protected Routes — auth flow

Protected Routes — Declarative vs Data mode

Declarative mode — перевірка через wrapper-компонент.

function ProtectedRoute({ children }) {
  const { isAuthenticated } = useAuth();

  if (!isAuthenticated)
    return <Navigate to="/login" replace />;

  return children;
}

<Route path="/dashboard" element={
  <ProtectedRoute>
    <DashboardLayout />
  </ProtectedRoute>
} />

Data mode — перевірка в loader до рендеру route.

import { redirect } from "react-router";

async function requireUser({ request }) {
  const user = await getCurrentUser(request);

  if (!user) {
    const url = new URL(request.url);
    const from = url.pathname + url.search;
    throw redirect(
      "/login?redirectTo=" +
      encodeURIComponent(from)
    );
  }

  return user;
}
const router = createBrowserRouter([
  {
    path: "/dashboard",
    loader: requireUser,
    Component: DashboardLayout,
    children: [
      { index: true, Component: DashboardHome },
      { path: "users", Component: UserList },
      { path: "settings", Component: Settings }
    ]
  }
]);

У Data mode перевірка відбувається на рівні route, тому окремий ProtectedRoute-wrapper не потрібен. Після login можна перейти за redirectTo. Для складнішого auth React Router також має route middleware.

Role-based Routes — Data mode

async function requireRole({ request }, roles: string[]) {
  const user = await requireUser({ request });

  if (!roles.includes(user.role)) {
    throw redirect("/forbidden");
  }

  return user;
}

const requireAdmin = (args: LoaderFunctionArgs) =>
  requireRole(args, ["admin"]);

const router = createBrowserRouter([
  {
    path: "/admin",
    loader: requireAdmin,
    Component: AdminPanel
  },
  {
    path: "/editor",
    loader: (args) =>
      requireRole(args, ["admin", "editor"]),
    Component: EditorPanel
  }
]);

Ідея: auth та permissions перевіряються до рендеру сторінки.

Перевага: одну функцію перевірки можна повторно використовувати для різних route.

Важливо: route guard не замінює перевірку прав на API/backend — сервер також має перевіряти доступ.

Lazy Loading Routes — Declarative vs Data mode

Declarative mode — React.lazy() для компонентів.

const Settings = lazy(
  () => import("./pages/Settings")
);

<Suspense fallback={<PageLoader />}>
  <Routes>...</Routes>
</Suspense>

Data mode — route.lazy завантажує route module.

const router = createBrowserRouter([
  {
    path: "/settings",
    lazy: async () => {
      const module = await import(
        "./pages/Settings"
      );
      return { Component: module.Settings };
    }
  }
]);

У Data mode route.lazy може завантажувати не лише компонент, а й loader або action. Це дозволяє тримати UI та логіку маршруту разом.

Lazy Loading Routes — Data mode: компонент + loader

const router = createBrowserRouter([
  {
    path: "/users/:id",
    lazy: async () => {
      const [page, data] = await Promise.all([
        import("./pages/UserDetails"),
        import("./pages/userLoader")
      ]);

      return {
        Component: page.UserDetails,
        loader: data.userLoader
      };
    }
  }
]);

route.lazy — code splitting для route configuration.

Router завантажує модуль перед відображенням цього маршруту.

Для Declarative mode використовується React.lazy + Suspense; для Data mode — route.lazy + route data APIs.

404 сторінка — Declarative та Data mode

Declarative mode:

<Route path="*" element={<NotFound />} />

Data mode:

const router = createBrowserRouter([
  { path: "/", Component: Home },
  { path: "/users", Component: UserList },
  { path: "*", Component: NotFound }
]);

path="*" — catch-all: спрацьовує, якщо жоден більш специфічний маршрут не збігся. React Router використовує ranking маршрутів.

Важливо: це 404 для UI. У SPA сервер може все одно віддавати index.html з HTTP 200. Для справжнього HTTP 404 потрібне налаштування сервера/CDN.

Архітектура застосунку

Структура React-застосунку

Шари відповідальності

Шар Відповідальність Приклад
App Глобальна конфігурація, провайдери RouterProvider, ThemeContext, ErrorBoundary
Layout Спільна оболонка сторінок Header, Nav, Footer + Outlet
Pages Сторінки, маршрути HomePage, UserListPage, SettingsPage
Features Доменна логіка (feature-first) auth/, products/, orders/
Components Перевикористовуваний UI Button, Modal, Input, Card
Hooks Спільна stateful-логіка useUsers, useDebounce, useAuth
API HTTP-клієнт, endpoint-функції apiClient, usersApi, productsApi
Types TypeScript-типи, DTO User, Product, CreateUserDTO

Feature-first структура — практичний варіант

src/
├── app/                    // глобальна конфігурація
│   ├── router.tsx
│   └── providers.tsx
├── pages/                  // route-level UI
├── features/               // функціональні модулі
└── shared/                 // справді спільний код
    ├── ui/
    ├── lib/
    └── types/

Feature-first — групуємо код за функціональністю. Для навчального проєкту достатньо цієї спрощеної схеми; повний FSD тут не потрібен.

Все для домена — в одній папці.

Container vs Presentational — класичний підхід

// Container — логіка всередині компонента
function UserListContainer() {
  const [users, setUsers] = useState<User[]>([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    usersApi.list()
      .then(setUsers)
      .catch(() => setError("Load failed"))
      .finally(() => setLoading(false));
  }, []);

  const handleDelete = async (id: string) => {
    await usersApi.delete(id);
    setUsers(prev => prev.filter(u => u.id !== id));
  };

  if (loading) return <Spinner />;
  if (error) return <ErrorView />;

  return (
    <UserListView
      users={users}
      onDelete={handleDelete}
    />
  );
}
// Presentational — тільки UI
function UserListView(props: {
  users: User[];
  onDelete: (id: string) => void;
}) {
  return (
    <ul>
      {props.users.map(user => (
        <li key={user.id}>
          {user.name}
          <button onClick={() => props.onDelete(user.id)}>
            Delete
          </button>
        </li>
      ))}
    </ul>
  );
}

Ідея: Container знає про state, API та бізнес-логіку, а Presentational-компонент отримує готові дані та callbacks і відповідає за UI.

Це класичний патерн. У сучасному React цю логіку часто виносять у Custom Hook — саме це покажемо на наступному слайді.

Сучасний підхід: логіка в Custom Hook

// 1. Логіку з Container виносимо в Hook
export function useUsers() {
  const [users, setUsers] = useState<User[]>([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    usersApi.list()
      .then(setUsers)
      .catch(() => setError("Load failed"))
      .finally(() => setLoading(false));
  }, []);

  const remove = async (id: string) => {
    await usersApi.delete(id);
    setUsers(prev => prev.filter(u => u.id !== id));
  };

  return { users, loading, error, remove };
}
// 2. Page/компонент використовує Hook
function UserListPage() {
  const { users, loading, error, remove } =
    useUsers();

  if (loading) return <Spinner />;
  if (error) return <ErrorView />;

  return (
    <UserListView
      users={users}
      onDelete={remove}
    />
  );
}

// UI залишається окремим
function UserListView({ users, onDelete }) {
  return /* тільки UI */;
}

Тепер state + effect + API + логіка не прив'язані до конкретного Container-компонента. Їх можна повторно використати в іншому компоненті, який викликає useUsers(). 

UserListPage ──┐
               ├── useUsers() ── users / loading / remove
UserStatistics ┘

Головна різниця: не «Container перейменували на Page», а логіку винесли з UI-компонента в окремий Hook.

1. children — базовий патерн

// Card — універсальна обгортка
function Card({ children, title }: {
  children: ReactNode;
  title: string;
}) {
  return (
    <div className="card">
      <h2>{title}</h2>
      <div className="card-body">
        {children}
      </div>
    </div>

// Використання

children — вбудований проп, передає дочірні елементи.

Призначення:

  • Layout-обгортки (Card, Panel, Modal);
  • Композиція без props drilling;
  • Реюзабельні UI-оболонки.

Перевага: Card не знає, що всередині — повна роздільність.

Аналог у Vue — <slot>.

TypeScript: children: ReactNode (не JSX.Element).

3. Render Props — функція як child

// Компонент приймає функцію-рендерер
function DataList<T>({
  items, renderItem
}: {
  items: T[];
  renderItem: (item: T) => ReactNode;
}) {
  return (
    <ul>
      {items.map((item, i) => (
        <li key={i}>{renderItem(item)}</li>
      ))}
    </ul>
  );
}

// Використання — callback як prop
<DataList
  items={users}
  renderItem={(user) => (
    <div>
      <h3>{user.name}</h3>
      <p>{user.email}</p>
    </div>
  )}
/>

Render prop — проп-функція, що повертає JSX.

Компонент делегує рендер викликучу.

Призначення:

  • Універсальні списки/таблиці;
  • Абстракція над data fetching;
  • Кастомізація рендеру.

Варіація — function as child:

<DataProvider>
  {(data) => <List items={data} />}
</DataProvider>

Зауваження: у сучасному React частіше замінюють на Custom Hooks.

  );
}

// Використання — передаємо готові елементи
<PageLayout
  header={<AppHeader />}
  sidebar={<NavMenu />}
>
  <UserListPage />  // children
</PageLayout>

Slot props — кілька «слотів» через окремі props типу ReactNode.

Призначення:

  • Складні layouts з кількома зонами;
  • Композиція без props drilling;
  • Page-specific контент у спільній оболонці.

Перевага над children: можна передати кілька окремих ділянок.

Аналог у Vue — <slot name="header">, <slot name="sidebar">.

В React Router <Outlet> — аналог slot для активного маршруту.

5. HOC (Higher-Order Component) — legacy

// HOC — функція, що приймає компонент і повертає новий
function withAuth<P>(
  Component: ComponentType<P>
) {
  return function Protected(props: P) {
    const { isAuthenticated } = useAuth();
    if (!isAuthenticated)
      return <Navigate to="/login" />;
    return <Component {...props} />;
  };
}

// Використання
export default withAuth(DashboardPage);

HOC — функція (Component) => NewComponent.

Історично: був основним патерном до Hooks (React < 16.8).

Зараз: для нового прикладного коду частіше використовують Hooks та wrapper-компоненти. HOC все ще зустрічаються в бібліотеках та legacy-коді.

Типові альтернативи:

  • Custom Hooks — для логіки;
  • Wrapper components — для UI;
  • ProtectedRoute — для auth.

Мінуси HOC:

  • втрата TypeScript-типізації props;
  • «wrapper hell» — вкладені HOC;
  • складно відлагоджувати (DevTools).

Порівняння патернів — коли використовувати

Патерн Коли використовувати Аналог Vue
children Обгортки, Layout, Card <slot>
Slot props Кілька зон (header, sidebar, main) <slot name="...">
Compound Tabs, Select, Accordion, Form provide/inject + slots
Render props Універсальні списки, data renderers scoped slot v-slot
Custom Hooks Перевикористання stateful-логіки (сучасний) Composables
HOC Legacy — не рекомендується —
Wrapper component Auth, Error Boundary, ProtectedRoute wrapper component

Composition — вирішення props drilling

// ❌ Props drilling
<App user={user}>
  <Layout user={user}>          // не потрібен
    <Sidebar user={user}>       // не потрібен
      <UserProfile user={user} />
    </Sidebar>
  </Layout>
</App>

// ✅ Composition — передаємо готовий елемент
<App>
  <Layout
    sidebar={
      <UserProfile user={user} />
    }
  />
</App>
// Layout не знає про user взагалі!

Композиція замість props drilling:

Замість прокидання user через Layout і Sidebar — передаємо готовий елемент <UserProfile> через slot prop.

Переваги:

  • Layout залишається агностичним;
  • Немає зайвих props;
  • Немає зайвих re-render;
  • Зрозуміло, де дані використовуються.

Альтернатива — Context API (Лекція 11), якщо user потрібен у багатьох місцях.

Архітектурні принципи — підсумок

  • Single Responsibility — кожен компонент має одну відповідальність;
  • Separation of Concerns — UI, логіка, data — окремі шари;
  • DRY — перевикористання через Custom Hooks + composition;
  • Composition over Inheritance — композиція є основним способом будувати повторно використовуваний UI;
  • Data-aware vs presentational — pages/features можуть працювати з data, а універсальні UI-компоненти краще тримати простими;
  • Feature-first — групування за доменом, не за типом файлу;
  • URL як state — клади в URL navigation state, який має бути shareable/bookmarkable; ephemeral UI state залишай у useState;
  • Lazy loading — code splitting для великих застосунків.

Типові помилки архітектури

  • Все в одному компоненті — 500-рядковий компонент з логікою, стилями, fetch. Рішення: розділити на Page + Hook + UI;
  • API-виклики в UI-компонентах — Button викликає axios. Рішення: Button лише emit подію, батько викликає API;
  • Props drilling через 5 рівнів — рішення: Context, composition, або lifting state;
  • Універсальний компонент «на всі випадки» — 50 props з умовами. Рішення: розділити на几个 спеціалізованих;
  • Навігаційний state в useState — якщо pagination/filter мають бути shareable/bookmarkable, збережи їх у URL через useSearchParams;
  • Занадто великий initial bundle — code splitting може зменшити початкове завантаження;
  • Без Error Boundary — одна помилка ламає весь застосунок. Рішення: ErrorBoundary per route/section.

Підсумок

  • SPA-маршрутизація — навігація без перезавантаження через History API. React Router — стандарт.
  • React Router: BrowserRouter, Routes, Route, Link, Outlet, Navigate. Hooks: useParams, useNavigate, useSearchParams, useLocation.
  • Route params (:id) + query params (?page=2) — URL як джерело правди.
  • Nested routes + <Outlet> — спільні layouts, ієрархія UI.
  • Protected routes — Declarative: <ProtectedRoute>; Data: route loader + redirect.
  • Lazy loading — Declarative: React.lazy + Suspense; Data: route.lazy.
  • Role-based routes — перевірка ролі на рівні route loader.
  • 404 — catch-all route path="*"; HTTP 404 окремо налаштовується на сервері/CDN.
  • Архітектура: App → Layouts → Pages → Features → Components. Feature-first структура.
  • Composition патерни: children, slot props, compound components, render props. HOC — legacy.
  • Custom Hooks замість Container-компонентів — сучасний підхід до розділення логіки та UI.
