План лекції:

  1. Як працюють форми в React та чим відрізняються controlled і uncontrolled components?

  3. Як побудувати authentication flow у React-застосунку?
  4. Як працюють JWT, authentication state та protected routes на frontend?

Форми в React

Форми в React — особливості

HTML уже має власну модель форм: браузер зберігає значення полів і виконує submit. React дає кілька способів підключитися до цієї моделі.

Ключові концепції:

  • Controlled components — React state є джерелом правди для input;
  • Uncontrolled components — DOM керує, React лише читає через ref;
  • Form submission — onSubmit + e.preventDefault();
  • Validation — перевірка перед submit та/або під час введення;
  • Error display — показ помилок per-field.

У Vue аналоги — v-model (controlled) та $refs (uncontrolled).

Controlled vs Uncontrolled

// Controlled (React керує)
const [name, setName] = useState("")
<input
  value={name}
  onChange={e => setName(e.target.value)}
/>
// state → input → state (loop)
// Uncontrolled (DOM керує)
const inputRef = useRef()
<input
  ref={inputRef}
  defaultValue="hello"
/>
// read: inputRef.current.value
  • Controlled: + single source of truth, validation on type, easy reset; − re-render on every keystroke.
  • Uncontrolled: + no re-render, simple for one-time read, integrate with non-React; − harder to validate, no live feedback.

Вибір: controlled зручний, коли React має бачити й змінювати значення під час роботи форми. Uncontrolled зручний, коли достатньо прочитати значення під час submit або треба працювати з DOM/API сторонньої бібліотеки.

Controlled Component — приклад

function LoginForm() {
  const [email, setEmail] = useState("");
  const [password, setPassword] = useState("");

  const handleSubmit = (e: FormEvent) => {
    e.preventDefault();
    console.log({ email, password });
    // API call...
  };

  return (
    <form onSubmit={handleSubmit}>
      <input
        type="email"
        value={email}
        onChange={(e) => setEmail(e.target.value)}
      />
      <input
        type="password"
        value={password}
        onChange={(e) => setPassword(e.target.value)}
      />
      <button type="submit">Login</button>
    </form>
  );
}

Controlled pattern:

  1. useState зберігає значення;
  2. value прив'язаний до state;
  3. onChange оновлює state;
  4. React контролює весь цикл.

Переваги:

  • Єдине джерело правди (state);
  • Валідація на льоту;
  • Легкий reset (setEmail(""));
  • Програмне встановлення значень.

Недолік: re-render на кожен keystroke (для більшості форм — не проблема).

Uncontrolled Component — приклад

import { useRef } from "react";

function QuickForm() {
  const emailRef = useRef<HTMLInputElement>(null);
  const fileRef = useRef<HTMLInputElement>(null);

  const handleSubmit = (e: FormEvent) => {
    e.preventDefault();
    const email = emailRef.current?.value;
    const file = fileRef.current?.files?.[0];
    console.log({ email, file });
  };

  return (
    <form onSubmit={handleSubmit}>
      <input type="email"
        ref={emailRef}
        defaultValue="old@example.com" />
      <input type="file"
        ref={fileRef} />
      <button type="submit">Submit</button>
    </form>
  );
}

Uncontrolled pattern:

  1. useRef посилається на DOM-вузол;
  2. defaultValue — початкове значення;
  3. Читаємо через ref.current.value при submit;
  4. React не керує значенням.

Коли використовувати:

  • <input type="file"> — значення не можна програмно встановити як звичайний input;
  • Інтеграція з 3rd-party (jQuery плагіни);
  • Прості форми без валідації;
  • Великі форми (щоб уникнути re-render).

Не існує абсолютного правила: вибір залежить від задачі форми.

Form lifecycle — стани

Багатопольна форма з одним state-об'єктом

type FormData = {
  name: string;
  email: string;
  age: number;
  role: string;
};

function UserForm() {
  const [form, setForm] = useState<FormData>({
    name: "", email: "", age: 0, role: "user"
  });

  const handleChange = (e: ChangeEvent) => {
    const { name, value, type } = e.target;
    setForm(prev => ({
      ...prev,
      [name]: type === "number"
        ? parseInt(value)
        : value
    }));
  };

  return (
    <form onSubmit={handleSubmit}>
      <input name="name" value={form.name}
        onChange={handleChange} />
      <input name="email" value={form.email}
        onChange={handleChange} />
      <input name="age" type="number"
        value={form.age} onChange={handleChange} />
      <select name="role" value={form.role}
        onChange={handleChange}>
        <option value="user">User</option>
        <option value="admin">Admin</option>
      </select>
    </form>
  );
}

Один state-об'єкт для всіх полів форми.

Переваги:

  • Один handleChange для всіх полів;
  • name атрибут = ключ у state;
  • Легко серіалізувати для API;
  • Легкий reset: setForm(initial).

Важливо: використовуйте функціональну форму setForm(prev => ...) щоб не втратити дані при швидкому введенні.

Checkbox: e.target.checked замість value.

select multiple: потребує окремої обробки.

Валідація форм

Валідація — типи правил

Валідація — коли перевіряти

// 1. On Submit
handleSubmit = (e) => {
  e.preventDefault();
  const errors = validate(form);
  if (Object.keys(errors).length)
    return setErrors(errors);
  submit(form);
}
// всі помилки одразу

Recommended approach

  1. onBlur → validate field when user leaves input (no annoying errors while typing);
  2. onChange → clear error when user starts fixing;
  3. onSubmit → validate all fields before submit.
// 2. On Change (live)
handleChange = (e) => {
  const { name, value } = e.target;
  setForm(f => ({...f, [name]: value}));
  const err = validateField(name, value);
  setErrors(e => ({...e, [name]: err}));
}
// помилки одразу при введенні

// 3. On Blur (recommended)
handleBlur = (e) => {
  const { name, value } = e.target;
  const err = validateField(name, value);
  setErrors(e => ({...e, [name]: err}));
}
// помилки коли поле
// втратило фокус

Валідація — ручний підхід

type FormErrors = { name?: string; email?: string; password?: string };

function validate(form: FormData): FormErrors {
  const errors: FormErrors = {};
  if (!form.name.trim()) errors.name = "Name is required";
  if (form.name.length < 2) errors.name = "Name too short";
  if (!/^\S+@\S+\.\S+$/.test(form.email)) errors.email = "Invalid email";
  if (form.password.length < 8) errors.password = "Min 8 characters";
  if (!/\d/.test(form.password)) errors.password = "Must contain a digit";
  return errors;
}

// Компонент
const [errors, setErrors] = useState<FormErrors>({});
const [touched, setTouched] = useState<Record<string, boolean>>({});

const handleBlur = (e) => {
  setTouched(t => ({ ...t, [e.target.name]: true }));
  const fieldErrors = validate(form);
  setErrors(prev => ({ ...prev, [e.target.name]: fieldErrors[e.target.name] }));
};

const handleSubmit = (e) => {
  e.preventDefault();
  const allErrors = validate(form);
  if (Object.keys(allErrors).length > 0) {
    setErrors(allErrors);
    setTouched({ name: true, email: true, password: true });
    return;
  }
  // submit
};

Валідація — UI відображення помилок

// Поле з помилкою
<div className="field">
  <label htmlFor="email">Email</label>
  <input
    id="email"
    name="email"
    value={form.email}
    onChange={handleChange}
    onBlur={handleBlur}
    className={errors.email && touched.email
      ? "input-error"
      : ""}
  />
  {errors.email && touched.email && (
    <p className="error">
      {errors.email}
    </p>
  )}
</div>

// CSS
.input-error {
  border-color: red;
}
.error {
  color: red; font-size: 10px;
}

Принципи UI помилок:

  • Показувати помилку тільки після touched (користувач зайшов у поле);
  • Прибирати помилку при початку виправлення;
  • Червоний border + текст під полем;
  • Aria-атрибути для accessibility: aria-invalid, aria-describedby;
  • Не блокувати введення — лише підказувати.

Подія onBlur — коли поле втратило фокус (найкращий момент для першої перевірки).

touched — об'єкт, що фіксує, які поля вже «відвідав» користувач.

React 19 — Form Actions

import { useActionState } from "react";
import { useFormStatus } from "react-dom";

async function submitName(
  previous: string,
  formData: FormData
) {
  const name = String(formData.get("name") ?? "");

  if (!name.trim())
    return "Name is required";

  await saveName(name);
  return "";
}

function Form() {
  const [error, action] =
    useActionState(submitName, "");

  return (
    <form action={action}>
      <input name="name" />
      <SubmitButton />
      {error && <p>{error}</p>}
    </form>
  );
}

function SubmitButton() {
  const { pending } = useFormStatus();

  return (
    <button type="submit" disabled={pending}>
      {pending ? "Saving..." : "Save"}
    </button>
  );
}

React 19 дозволяє передавати функцію як form action.

useActionState поєднує submit із результатом action та станом виконання.

useFormStatus дозволяє компоненту всередині форми дізнатися, чи триває submit.

Це не заміна RHF + Zod у всіх випадках. Для складних клієнтських форм RHF + schema validation може бути зручнішим.

Authentication Flow

Authentication Flow — повний цикл

Auth — архітектура

Authentication — перевірка, хто користувач (login + password).

Authorization — перевірка, що користувач може робити (role, permissions).

Компоненти auth-системи:

  • AuthContext — спільний auth state для UI (user, isAuthenticated, loading);
  • useAuth hook — доступ до auth state + методів (login, logout, register);
  • API layer — authApi.login(), authApi.me();
  • ProtectedRoute — wrapper для захищених сторінок;
  • Axios interceptor — додає token до всіх запитів;
  • Token/session storage — спосіб залежить від архітектури; для browser-сесій часто використовують HttpOnly cookie.
  • Route protection — у Declarative mode wrapper; у Data mode route loader/middleware.

Auth Context — архітектура

AuthContext — реалізація

const AuthContext = createContext<AuthState | null>(null);

// login → setUser(user)
// logout → setUser(null)

AuthContext — спільний auth state для UI. useAuth() дає компонентам доступ до цього state та auth actions.

useAuth hook — використання

// LoginPage.tsx
function LoginPage() {
  const { login } = useAuth();
  const navigate = useNavigate();
  const location = useLocation();
  const [error, setError] = useState(null);

  const from = location.state?.from?.pathname
    || "/dashboard";

  const handleSubmit = async (data) => {
    try {
      await login(data.email, data.password);
      navigate(from, { replace: true });
    } catch (e) {
      setError("Invalid credentials");
    }
  };

  return (
    <LoginForm
      onSubmit={handleSubmit}
      error={error}
    />
  );
}
// Navbar.tsx — показ залежно від auth
function Navbar() {
  const { user, isAuthenticated, logout } =
    useAuth();
  const navigate = useNavigate();

  const handleLogout = () => {
    logout();
    navigate("/login");
  };

  return (
    <nav>
      {isAuthenticated ? (
        <>
          <span>Hello, {user.name}</span>
          <button onClick={handleLogout}>
            Logout
          </button>
        </>
      ) : (
        <Link to="/login">Login</Link>
      )}
    </nav>
  );
}

JWT та Protected Routes

JWT (JSON Web Token) — структура

JWT — як це працює

JWT — компактний формат token-а для передачі claims між сторонами. Типовий запис: header.payload.signature.

  • Header — метадані token-а та алгоритм;
  • Payload — claims, наприклад sub, role, exp;
  • Signature — перевіряє цілісність token-а відповідно до алгоритму (наприклад, HMAC або RSA/ECDSA).

Важливо: payload зазвичай не шифрується. Його можна декодувати, тому секретні дані туди не кладуть.

JWT не означає автоматично "stateless". Його можна використовувати і в системах із серверною перевіркою/відкликанням token-ів.

Токен зберігання — варіанти

localStorage/sessionStorage доступні JavaScript, тому XSS може викрасти token.

HttpOnly + Secure cookie не можна прочитати через JavaScript, але cookie автоматично надсилаються браузером, тому треба враховувати CSRF. SameSite і додатковий CSRF-захист залежать від архітектури.

Для навчального SPA: localStorage можна використати для демонстрації механіки, але не подавати як рекомендоване production-рішення.

Axios interceptor — додаємо token

// api/client.ts
import axios from "axios";

export const apiClient = axios.create({
  baseURL: "https://api.example.com",
});

// Request interceptor — додаємо Authorization header
apiClient.interceptors.request.use((config) => {
  const token = localStorage.getItem("token");
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});

// Response interceptor — 401 → logout + redirect
apiClient.interceptors.response.use(
  (response) => response,
  (error) => {
    if (error.response?.status === 401) {
      localStorage.removeItem("token");
      window.location.href = "/login";
    }
    return Promise.reject(error);
  }
);

Цей приклад розрахований на token, доступний JavaScript. Якщо auth використовує HttpOnly cookie, JavaScript не читає token і такий request interceptor для Authorization header не потрібен. При 401 застосунок може очистити auth state, запустити refresh flow або показати login — залежно від архітектури.

Protected Routes + Auth — зв'язок

ProtectedRoute — з AuthContext

// components/ProtectedRoute.tsx
import { Navigate, useLocation }
  from "react-router";
import { useAuth } from "../context/AuthContext";

export function ProtectedRoute({
  children, roles = []
}: {
  children: ReactNode;
  roles?: string[];
}) {
  const { user, isAuthenticated, loading } =
    useAuth();
  const location = useLocation();

  // Auth check in progress
  if (loading) return <FullScreenLoader />;

  if (!isAuthenticated)
    return <Navigate to="/login"
      state={ from: location } replace />;

  // Role check
  if (roles.length > 0 &&
      !roles.includes(user!.role))
    return <Navigate to="/forbidden" replace />;

  return <>{children}</>;
}
// App.tsx — структура з AuthProvider
<AuthProvider>
  <BrowserRouter>
    <Routes>
      <Route path="/login"
        element={<LoginPage />} />

      <Route path="/dashboard" element={
        <ProtectedRoute>
          <DashboardLayout />
        </ProtectedRoute>
      }>
        <Route index
          element={<DashboardHome />} />
        <Route path="users"
          element={<UserList />} />
      </Route>

      <Route path="/admin" element={
        <ProtectedRoute
          roles={["admin"]}>
          <AdminPanel />
        </ProtectedRoute>
      } />
    </Routes>
  </BrowserRouter>
</AuthProvider>

loading стан — поки AuthContext перевіряє session/token при завантаженні сторінки. Без нього — при reload користувача можна помилково редиректити до завершення перевірки. У Data mode цю перевірку також можна виконувати в route loader або middleware.

Security threats — XSS та CSRF

Auth — типові помилки

  • Зберігати bearer token у localStorage без урахування XSS — шкідливий JavaScript може прочитати token. Рішення: не використовувати небезпечний HTML без санітизації; CSP — додатковий захист;
  • Без loading-стану при перевірці token — при reload користувача одразу редиректить на /login. Рішення: loading в AuthContext;
  • Token не видаляється при logout — залишається в localStorage. Рішення: localStorage.removeItem + очистка state;
  • Неправильно обробляти 401 — застосунок не синхронізує auth state з API. Варіант рішення: response interceptor, refresh або logout — залежно від auth-схеми;
  • Немає перевірки permissions для route, який її потребує — одного isAuthenticated недостатньо. Додайте role/permission check;
  • Пароль у state без type="password" — видно на екрані. Рішення: завжди type="password";
  • Frontend валідація як єдина — обхід через curl. Рішення: backend обов'язково валідує.

Registration flow — реєстрація

function RegisterPage() {
  const { login } = useAuth();
  const navigate = useNavigate();
  const [serverError, setServerError] =
    useState(null);

  const handleSubmit = async (data) => {
    try {
      // 1. Register
      await authApi.register(data);
      // 2. Auto-login через єдиний auth flow
      await login(data.email, data.password);
      // 3. Redirect
      navigate("/dashboard");
    } catch (e) {
      setServerError(e.response?.data?.message
        || "Registration failed");
    }
  };

  return <RegisterForm
    onSubmit={handleSubmit}
    serverError={serverError} />;
}

Registration кроки:

  1. Форма: name, email, password, confirm;
  2. Frontend валідація (Zod schema);
  3. POST /api/register;
  4. Успіх → auto-login (зберегти token);
  5. Редирект на /dashboard;
  6. Помилка (email exists) → показати serverError.

Валідація password confirm:

Zod: .refine(data => data.password === data.confirm)

Server errors (email exists) — показуємо як serverError окремо від field errors.

Password handling — безпека

Основні правила:

  • Ніколи не логувати пароль і не зберігати його без потреби після submit;
  • type="password" — приховує введення в UI;
  • autocomplete="new-password" для registration;
  • autocomplete="current-password" для login;
  • Хешування — на backend (наприклад, Argon2id або bcrypt), не на frontend;
  • HTTPS — обов'язковий для передачі credentials;
  • Не вимагайте довільних "букви + цифри + спецсимволи" як універсальне правило. Актуальні рекомендації NIST роблять акцент на довжині та blocklist скомпрометованих паролів.
  • Мінімальна довжина залежить від моделі автентифікації: NIST SP 800-63B-4 вимагає 15 символів для single-factor password і дозволяє 8+ у складі MFA.

Підсумок

  • Controlled — React state керує значенням поля. Uncontrolled — DOM зберігає значення, React читає його через ref або Form API.
  • Валідація — можна виконувати onBlur/onChange/onSubmit; UX залежить від форми.
  • React Hook Form + Zod — практичний варіант для складних форм: form state + schema validation + TS types.
  • React 19 Forms — form action, useActionState, useFormStatus спрощують частину submit-flow.
  • Frontend validation ≠ security — backend обов'язково перевіряє credentials та permissions.
  • Authentication vs Authorization: хто користувач + що йому дозволено.
  • Auth state можна тримати через Context для UI; route protection у Data mode можна будувати через loader/middleware.
  • JWT має header/payload/signature; payload не є шифрованим за замовчуванням.
  • Token storage: localStorage доступний JavaScript і вразливий до викрадення при XSS; HttpOnly cookie захищає token від читання JavaScript, але потребує CSRF-захисту.
  • Axios interceptor корисний для bearer token, який додається JavaScript; cookie-based auth працює інакше.
  • Token refresh — окремий advanced flow, який залежить від backend та способу зберігання refresh token.
