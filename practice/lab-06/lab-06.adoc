=== Теоретична частина

==== Feature-Sliced Design

Feature-Sliced Design (FSD) - архітектурна методологія для організації коду фронтенд-застосунків.
Вона задає єдині правила того, *де* розміщувати код та *які модулі можуть залежати від яких*.
Це робить структуру проєкту передбачуваною, спрощує навігацію по коду, масштабування й командну роботу.

Код у FSD ділиться на три рівні організації: *шари (layers)*, *слайси (slices)* та *сегменти (segments)*.

*Шари* розташовані від найвищого до найнижчого:

[cols="1,3",options="header"]
|===
|Шар |Призначення

|`app` |Все, що робить застосунок працюючим: ініціалізація, роутер, провайдери (Pinia, UI-бібліотека), глобальні стилі, реєстрація сервісів.
|`pages` |Сторінки застосунку (один слайс - одна сторінка, зазвичай відповідає маршруту).
|`widgets` |Великі самодостатні блоки інтерфейсу, що складаються з features та entities (шапка сайту, таблиця користувачів).
|`features` |Дії користувача, що мають бізнес-цінність (вхід у систему, створення користувача, пошук).
|`entities` |Бізнес-сутності предметної області (user, session): типи, сервіси, store.
|`shared` |Перевикористовуваний код без прив'язки до бізнес-логіки: HTTP-клієнт, UI-кіт, утиліти, конфіг.
|===

Шари `app` та `shared` не діляться на слайси, а складаються безпосередньо із сегментів.

*Слайси* - це розбиття всередині шару за предметною областю (наприклад, `entities/user`, `features/auth`, `pages/users`).

*Сегменти* - розбиття слайса за технічним призначенням.
Типові назви:

* `ui` - компоненти;
* `model` - стан, типи, бізнес-логіка (сюди належать Pinia store);
* `api` - взаємодія із зовнішніми джерелами даних (сюди належать репозиторії/сервіси);
* `lib` - допоміжні функції слайса;
* `config` - константи та конфігурація.

*Головні правила залежностей:*

. Модуль може імпортувати лише з шарів, що розташовані *нижче* за нього (наприклад, `features` може імпортувати з `entities` і `shared`, але не з `widgets`).
. Слайси одного шару *не імпортують один одного* (`features/auth` не може імпортувати з `features/user-form`).
. Слайс відкриває назовні лише *Public API* - файл `index.ts`, що реекспортує дозволені частини.
Імпорт «вглиб» слайса (`entities/user/model/store`) заборонений.

Приклад Public API слайса:

[source,ts]
----
// src/entities/user/index.ts
export type { User, CreateUserDto, UpdateUserDto } from './model/types'
export { UserService } from './api/user.service'
export { useUsersStore } from './model/users.store'

==== Repository у структурі FSD

Патерн Repository з лабораторної №5 зберігається, але його складові розподіляються по шарах:

[cols="1,2",options="header"]
|===
|Частина |Розташування

|HTTP-клієнт, інтерфейси `Readable`, `Creatable`, `Editable`, `Deletable` |`shared/api`
|`User`, `CreateUserDto`, `UpdateUserDto` |`entities/user/model`
|`UserService` |`entities/user/api`
|`ServiceProvider` (реєстр сервісів) |`shared/api`
|Реєстрація `UserService` та `AuthService` у `ServiceProvider` |`app/providers`
|===

Зверніть увагу: `ServiceProvider` з лабораторної №5 імпортує `UserService` напряму.
У FSD шар `shared` не може залежати від `entities`, тому провайдер перетворюється на *універсальний реєстр*, а конкретні сервіси реєструються на рівні `app` (шар `app` може імпортувати все):

[source,ts]
----
// src/shared/api/service-provider.ts
type Factory<T> = () => T

export class ServiceProvider {
    private static factories = new Map<string, Factory<unknown>>()
    private static instances = new Map<string, unknown>()

    static register<T>(key: string, factory: Factory<T>): void {
        this.factories.set(key, factory)
    }

    static get<T>(key: string): T {
        if (!this.instances.has(key)) {
            const factory = this.factories.get(key)
            if (!factory) throw new Error(`Service "${key}" is not registered`)
            this.instances.set(key, factory())
        }
        return this.instances.get(key) as T
    }
}
----

[source,ts]
----
// src/app/providers/services.ts
import { ServiceProvider } from '@/shared/api'
import { UserService } from '@/entities/user'

export function registerServices(): void {
    ServiceProvider.register('users', () => new UserService())
}
----

==== Pinia

Pinia - офіційна бібліотека керування станом для Vue 3.
Store - це реактивний об'єкт, доступний з будь-якого компонента, що зберігає спільний стан застосунку.

Основні поняття:

* *state* - реактивні дані (`ref`);
* *getters* - обчислювані значення (`computed`);
* *actions* - функції, що змінюють стан (у тому числі асинхронні).

Рекомендований для цієї роботи підхід - *setup stores*, які використовують Composition API:

[source,ts]
----
// src/entities/user/model/users.store.ts
import { ref, computed } from 'vue'
import { defineStore } from 'pinia'
import { ServiceProvider } from '@/shared/api'
import type { UserService } from '../api/user.service'
import type { User, CreateUserDto, UpdateUserDto } from './types'

export const useUsersStore = defineStore('users', () => {
    const users = ref<User[]>([])
    const total = ref(0)
    const isLoading = ref(false)
    const error = ref<string | null>(null)

    const hasUsers = computed(() => users.value.length > 0)

    const service = () => ServiceProvider.get<UserService>('users')

    async function fetchUsers(limit = 10, skip = 0) {
        isLoading.value = true
        error.value = null
        try {
            const data = await service().getAll({ limit, skip })
            users.value = data.users
            total.value = data.total
        } catch (e) {
            error.value = (e as Error).message
        } finally {
            isLoading.value = false
        }
    }

    async function removeUser(id: number) {
        await service().delete(id)
        // Оскільки DummyJSON лише імітує видалення, то оновлюємо локальний стан самостійно
        users.value = users.value.filter((u) => u.id !== id)
    }

    return { users, total, isLoading, error, hasUsers, fetchUsers, removeUser }
})
----

Використання в компоненті.
Для збереження реактивності при деструктуризації state та getters використовується `storeToRefs`, а actions деструктуризуються напряму:

[source,vue]
----
<script setup lang="ts">
import { onMounted } from 'vue'
import { storeToRefs } from 'pinia'
import { useUsersStore } from '@/entities/user'

const store = useUsersStore()
const { users, isLoading, error } = storeToRefs(store)
const { fetchUsers } = store

onMounted(() => fetchUsers())
</script>
----

Store авторизації (сесії) зберігає токени та поточного користувача і синхронізується з `localStorage`:

[source,ts]
----
// src/entities/session/model/session.store.ts
import { ref, computed } from 'vue'
import { defineStore } from 'pinia'

const STORAGE_KEY = 'session'

export const useSessionStore = defineStore('session', () => {
    const accessToken = ref<string | null>(localStorage.getItem(`${STORAGE_KEY}:token`))
    const isAuthenticated = computed(() => accessToken.value !== null)

    function setSession(token: string) {
        accessToken.value = token
        localStorage.setItem(`${STORAGE_KEY}:token`, token)
    }

    function clearSession() {
        accessToken.value = null
        localStorage.removeItem(`${STORAGE_KEY}:token`)
    }

    return { accessToken, isAuthenticated, setSession, clearSession }
})
----

Store можна використовувати й поза компонентами (наприклад, у navigation guard), але лише після того, як Pinia встановлено в застосунку:

[source,ts]
----
// src/app/providers/router/guards.ts
import type { Router } from 'vue-router'
import { useSessionStore } from '@/entities/session'

export function setupGuards(router: Router): void {
    router.beforeEach((to) => {
        const session = useSessionStore()
        if (to.meta.requiresAuth && !session.isAuthenticated) {
            return { name: 'login', query: { redirect: to.fullPath } }
        }
    })
}
----

==== UI-бібліотеки компонентів

UI-бібліотека надає готові компоненти (кнопки, поля, таблиці, діалоги, сповіщення), тематизацію та доступність, що пришвидшує розробку.
Для Vue 3 поширені PrimeVue, Naive UI, Element Plus, Vuetify, Quasar, Ant Design Vue, а також підхід «copy-paste» із shadcn-vue та Tailwind CSS.

При виборі та інтеграції слід звертати увагу на:

. *Tree-shaking* - підключаються лише використані компоненти (імпорт окремих компонентів або auto-import), щоб не збільшувати розмір бандлу;
. *Тематизація* - можливість налаштувати кольори та типографіку під застосунок;
. *Залежність від бібліотеки* - використання компонентів бібліотеки напряму в усьому коді ускладнює її заміну.

Для зменшення залежності компоненти бібліотеки *обгортаються* в тонкі власні компоненти, які розміщуються в `shared/ui`.
Решта застосунку використовує лише `AppButton`, `AppInput` тощо, тому заміна бібліотеки зачіпає один шар:

[source,vue]
----
<!-- src/shared/ui/AppButton/AppButton.vue (приклад на PrimeVue) -->
<script setup lang="ts">
import Button from 'primevue/button'

defineProps<{
    label: string
    loading?: boolean
    severity?: 'secondary' | 'danger'
}>()

defineEmits<{ click: [event: MouseEvent] }>()
</script>

<template>
    <Button
        :label="label"
        :loading="loading"
        :severity="severity"
        @click="$emit('click', $event)"
    />
</template>
----

Public API шару `shared/ui`:

[source,ts]
----
// src/shared/ui/index.ts
export { default as AppButton } from './AppButton/AppButton.vue'
export { default as AppInput } from './AppInput/AppInput.vue'
export { default as AppTable } from './AppTable/AppTable.vue'
export { default as AppConfirmDialog } from './AppConfirmDialog/AppConfirmDialog.vue'
----

=== Завдання:

Використовуючи застосунок vue-lottery-app (результат лабораторної №5), виконати наступне:

** Виконати самостійну роботу студента.
** Створити гілку `feature/fsd` від `feature/routing`.
** *Структура FSD.* Реорганізувати проєкт відповідно до шарів `app`, `pages`, `widgets`, `features`, `entities`, `shared`:
*** Налаштувати alias `@` → `src` (у `vite.config.ts` та `tsconfig`);
*** `app` - `main.ts`, `App.vue`, роутер із guard-ами, реєстрація сервісів, підключення Pinia та UI-бібліотеки, глобальні стилі;
*** `pages` - Home, About, Users, UserDetails, Login, NotFound;
*** `widgets` - `AppHeader` (разом з `AppNavigation` та `Logo`), `UsersTable`;
*** `features` - `auth` (форма входу, кнопка Logout), `user-form` (створення й редагування користувача з валідацією VeeValidate);
*** `entities` - `user` (типи, `UserService`, store), `session` (store, токени);
*** `shared` - HTTP-клієнт, інтерфейси Repository, `ServiceProvider`, UI-обгортки, конфіг.
** Кожен слайс повинен мати файл `index.ts` (Public API); імпорти між слайсами та шарами виконуються *лише* через нього.
** Налаштувати лінтер правил FSD (Steiger або `eslint-plugin-boundaries`) так, щоб порушення напрямку залежностей та глибокі імпорти були помилками.
Додати npm-скрипт `lint:fsd`.
Усі помилки лінтера мають бути виправлені.
** *Repository у FSD.* Перенести складові патерну Repository згідно з таблицею в теоретичній частині.
Перетворити `ServiceProvider` на універсальний реєстр (без імпортів з `entities`), а реєстрацію `UserService` і `AuthService` винести в `app/providers/services.ts`.
** *Pinia.* Підключити Pinia та реалізувати:
*** `useSessionStore` (токени, ознака авторизації, методи `setSession` / `clearSession`) - замінити попереднє зберігання стану авторизації;
*** `useUsersStore` (список, загальна кількість, `isLoading`, `error`, дії `fetchUsers`, `fetchUser`, `createUser`, `updateUser`, `removeUser`);
*** використати setup stores та `storeToRefs`;
*** після створення, редагування та видалення користувача оновлювати стан у store (DummyJSON імітує запис).
** Компоненти сторінок і віджетів не повинні звертатися до сервісів напряму - лише через стори.
** *UI-бібліотека.* Обрати одну бібліотеку (рекомендовано PrimeVue; допускається Naive UI або Element Plus; інша - за погодженням з викладачем) та:
*** підключити лише необхідні компоненти (auto-import або імпорт окремих компонентів);
*** створити в `shared/ui` обгортки: `AppButton`, `AppInput` (з відображенням помилки валідації), `AppTable`, `AppConfirmDialog` (підтвердження видалення користувача);
*** використати обгортки на сторінках і у віджетах, жодного прямого імпорту компонентів бібліотеки поза `shared/ui` та `app/providers/ui.ts`;
*** використати компонент сповіщень (toast/message) для результату операцій (користувача створено, оновлено, видалено, помилка авторизації);
*** налаштувати тему (основний колір) відповідно до стилю застосунку.
** Інтегрувати VeeValidate з обгортками `AppInput` у формах входу та користувача.
** Переконатися, що функціонал лабораторної №5 працює без регресій: навігація, `/users/:id`, пагінація й пошук через query-параметри, авторизація, захист маршрутів, сторінка 404.
** Додати перемикач світлої/темної теми (Store налаштувань у `entities` або `features`, збереження у `localStorage`).
** Додати плагін збереження стану Pinia (`pinia-plugin-persistedstate`) і порівняти з ручною реалізацією у `session.store.ts`.
** Додати діаграму залежностей шарів проєкту до `README.md` (наприклад, у Mermaid).
