= Лабораторна робота №12

*Тема:* Підсумковий курсовий проєкт: modern React, API, state management та архітектура застосунку.

*Мета:* самостійно спроєктувати та реалізувати завершений SPA-застосунок, використовуючи підходи та інструменти, вивчені протягом курсу React.

Це *фінальний проєкт курсу*. На відміну від робіт №8–11, студент самостійно визначає структуру застосунку, спосіб взаємодії його частин та конкретні деталі реалізації.

Від виконавця очікується не покрокова реалізація окремих технологій, а завершений продукт із логічною архітектурою та цілісним користувацьким сценарієм.

== Технологічний стек

Проєкт виконувати на актуальному стеку курсу:

* React 19.x;
* Node.js 22.22 або новіша версія;
* TypeScript;
* React Router 8;
* TanStack Query v5;
* Zustand v5;
* React Hook Form + Zod.

Підходи до стилізації:

* SCSS + BEM;
* Bootstrap;
* Tailwind CSS.

Обрати один підхід та використовувати його послідовно.

== Архітектура

Студент самостійно обирає спосіб організації коду:

* **feature-first** — переважно за функціональністю;
* **type-first** — переважно за технічною відповідальністю.

Повний FSD не вимагається.

Незалежно від обраної структури повинні бути зрозумілими:

* відповідальність модулів;
* межа між UI та data-access;
* напрямок залежностей;
* місце зберігання server state та client/UI state.

Для роботи із server-side даними **Repository є обов'язковим**.

== Server state та client state

Server state організувати за допомогою **TanStack Query**, client/UI state — за допомогою **Zustand**.

Не дублювати один і той самий server state у Zustand.

Client-owned state повинен мати реальну роль у користувацькому сценарії та зберігатися між перезавантаженнями, якщо це доречно для обраної предметної області.

== API та Repository

Застосунок повинен працювати із зовнішнім API або іншим зовнішнім джерелом server state.

Repository повинен відокремлювати UI від деталей API та HTTP-взаємодії.

Для основної предметної сутності передбачити операції, необхідні для реалізованого сценарію.

Якщо формат API-відповіді не збігається з моделлю, яку використовує UI, це потрібно коректно ізолювати на data-access рівні.

== Варіанти курсового проєкту

Вибрати одну з 10 предметних областей:

. **Mini Shop** — каталог товарів, категорії, пошук, сортування, деталі, кошик та обране.
. **Movie Explorer** — каталог фільмів, жанри, пошук, деталі, watchlist та власні оцінки.
. **Book Tracker** — каталог книг, пошук, деталі, статус читання та власна бібліотека.
. **Recipe Planner** — каталог рецептів, фільтри, деталі, обране та план харчування.
. **Travel Planner** — напрямки, пошук, деталі, збережені місця та власний маршрут подорожі.
. **Event Planner** — каталог подій, фільтри, деталі, обране та власні події.
. **Job Board** — список вакансій, пошук, фільтри, деталі, збережені вакансії та статус подачі.
. **Workout Planner** — каталог тренувань, фільтри, деталі, власний план та відмітка виконання.
. **Pet Adoption** — каталог тварин, фільтри, деталі, обране та заявки на усиновлення.
. **Music Explorer** — каталог виконавців або треків, пошук, жанри, деталі, favorites та власні playlist-и.

Для кожної теми предметні сценарії потрібно адаптувати до її змісту.

Іншу предметну область можна обрати за погодженням з викладачем.

== Обов'язковий функціонал

Готовий проєкт повинен містити:

. щонайменше **дві пов'язані server-side сутності або ресурси**;
. список основної сутності та сторінку її детального перегляду;
. щонайменше **чотири змістовні маршрути**;
. dynamic route та query-param сценарій;
. пошук або фільтрацію;
. сортування;
. pagination або infinite scroll;
. щонайменше одну значущу CRUD/mutation-операцію;
. щонайменше **дві форми**, одна з яких виконує реальну предметну операцію;
. Zod-валідацію;
. окремий client/UI state через Zustand;
. persistence для client-owned state;
. Repository для роботи із server-side даними;
. щонайменше **два повторно використовувані UI-компоненти**;
. loading, error, empty та success states;
. pending state під час mutation;
. можливість повторити невдалу асинхронну операцію;
. щонайменше **три автоматизовані тести**.

Якщо обране API не підтримує потрібну mutation, дозволено реалізувати CRUD для власної client-owned сутності. Основний server state при цьому все одно повинен працювати через TanStack Query.

== Якість та завершеність

Проєкт повинен:

* мати цілісний користувацький сценарій від початку до кінця;
* коректно обробляти помилки та порожні результати;
* не дублювати state без потреби;
* мати зрозуміле розділення відповідальності;
* не використовувати `alert` як основний механізм повідомлень;
* проходити ESLint та TypeScript checks;
* містити README з коротким описом, інструкцією запуску та архітектурними рішеннями;
* мати deployed version, доступну за посиланням.

Git-процес продовжувати за правилами попередніх лабораторних.
До захисту репозиторій повинен містити осмислену історію комітів.

== Тести

Написати щонайменше три автоматизовані тести.

Тести повинні перевіряти важливі частини проєкту, а не лише тривіальні utility-функції.

Під час вибору, що тестувати, орієнтуватися на критичні для користувача сценарії, бізнес-логіку та data-access.

Конкретний стек тестування студент може обрати самостійно.

== Додаткові можливості

Для підвищення оцінки реалізувати щонайменше **два** додаткові пункти:

. optimistic update;
. lazy routes або code splitting;
. prefetch даних;
. dependent queries;
. складна domain-specific feature;
. темна тема з persistence;
. розширена keyboard accessibility / ARIA;
. додаткові component tests;
. рольова модель або authorization;
. offline-friendly UX;
. інший обґрунтований client-owned workflow.

Додаткові можливості оцінюються за якістю реалізації, а не за кількістю.
