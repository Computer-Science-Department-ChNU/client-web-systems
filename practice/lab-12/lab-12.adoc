= Лабораторна робота №12

*Тема:* Підсумковий курсовий mini-project: modern React, API, server/client state та архітектура застосунку.

*Мета:* самостійно спроєктувати та реалізувати завершений SPA-застосунок, використовуючи підходи та інструменти, вивчені протягом курсу React.

Це *фінальний проєкт курсу*. Він повинен показати не лише знання окремих React API, а здатність самостійно спроєктувати невеликий, але цілісний застосунок: від маршрутизації та API до форм, state management, UX, тестів та структури коду.

На відміну від робіт №8–11, предметну область студент обирає самостійно із запропонованих варіантів.

== Розподіл state

TanStack Query використовується для даних, джерелом яких є сервер, а Zustand — для стану, який належить самому клієнтському застосунку.

Приклади client-owned state:

* кошик;
* обране;
* watchlist;
* план подорожі;
* власні фільтри або UI-налаштування;
* список збережених вакансій;
* локальний план тренувань.

Не потрібно дублювати один і той самий server state в TanStack Query та Zustand.

Похідні значення повинні обчислюватися зі state, а не підтримуватися окремим дубльованим state без потреби.

== Архітектурний підхід

У цій лабораторній **не потрібно реалізовувати повний FSD** і не потрібно дотримуватися конкретних назв папок.

Студент може обрати один із двох підходів:

. **feature-first** — код групується переважно за функціональністю;
. **type-first** — код групується переважно за технічною відповідальністю.

Головне — щоб відповідальність модулів була зрозумілою, залежності були логічними, а API-доступ не був змішаний з UI-кодом.

Приклад спрощеної feature-first структури:

[source]
----
src/
├── app/
├── pages/
├── features/
└── shared/
----

Приклад спрощеної type-first структури:

[source]
----
src/
├── app/
├── pages/
├── components/
├── hooks/
├── repositories/
├── services/
├── store/
└── types/
----

Це лише орієнтири.
Структура може відрізнятися, якщо вона залишається зрозумілою.

Не потрібно створювати окрему папку або шар для кожного типу файлів лише заради шаблону.

== Repository та API boundary

Repository є обов'язковим.

API-запити та побудова endpoint URL повинні бути винесені за межі page/component-рівня.

Рекомендований напрямок залежностей:

[source]
----
Page / Component
       ↓
Repository
       ↓
API client / HTTP
       ↓
External API
----

Repository повинен надавати зрозумілі операції предметної області, наприклад:

[source,typescript]
----
productRepository.getList(params)
productRepository.getById(id)
productRepository.create(data)
productRepository.update(id, data)
productRepository.remove(id)
----

Конкретні назви та набір методів залежать від предметної області.

Компоненти та сторінки:

* не повинні вручну будувати endpoint URL;
* не повинні дублювати HTTP-код;
* не повинні знати деталі DTO API, якщо вони вже перетворені в domain-модель.

Якщо API-модель відрізняється від моделі, яку використовує UI, створити окреме mapping-рішення на data-access рівні.

== Мінімальна функціональність

Незалежно від обраної теми готовий застосунок повинен містити:

. щонайменше **дві пов'язані server-side сутності або server-side ресурси**;
. список основної сутності;
. сторінку детального перегляду;
. щонайменше **чотири маршрути**;
. пошук або фільтрацію;
. сортування;
. pagination або infinite scroll;
. route params та query params там, де вони мають зміст;
. створення або редагування сутності;
. видалення або іншу значущу mutation;
. окремий client/UI state через Zustand;
. persistence для client-owned state;
. щонайменше **дві форми**, одна з яких повинна мати реальну mutation-операцію;
. валідацію форм через Zod;
. Repository для server-side даних;
. щонайменше два повторно використовувані UI-компоненти;
. loading, error, empty та success states;
. зрозумілий pending state під час mutation;
. можливість повторити операцію після помилки завантаження;
. щонайменше три автоматизовані тести.

Якщо обране зовнішнє API не підтримує потрібні mutation, дозволено реалізувати CRUD для власної client-owned сутності.

Водночас робота з основним server state все одно повинна проходити через TanStack Query та Repository.

== 1. TanStack Query — server state

Створити та підключити `QueryClient`.

Використати щонайменше:

* `useQuery`;
* `useMutation`.

Обов'язково реалізувати:

* query для списку;
* query для детального перегляду;
* query key, який залежить від search/filter/sort/pagination параметрів;
* mutation create, update або delete;
* invalidation або інше коректне оновлення пов'язаного query після mutation.

Дані API повинні залишатися в TanStack Query.

Не переносити response із API у Zustand лише для того, щоб замінити query cache.

Додатково реалізувати **один** із варіантів:

* dependent query;
* prefetch деталей;
* prefetch наступної сторінки;
* окремий mutation з optimistic update.

== 2. Zustand — client/UI state

Створити щонайменше один store.

Client state повинен мати реальне значення для UX або бізнес-сценарію.

Наприклад:

* кошик;
* favorites/watchlist;
* план подорожі;
* власний план тренувань;
* локальна колекція;
* UI preferences.

Для цього state реалізувати persistence після перезавантаження сторінки.

Не зберігати server state у Zustand.

Якщо state містить складні об'єкти, уникати дублювання derived values.
Наприклад, загальна сума кошика повинна обчислюватися з його items.

== 3. Routing

Застосунок повинен мати щонайменше чотири змістовні маршрути.

Рекомендований варіант:

[source]
----
/
├── /items
├── /items/:itemId
├── /saved
└── /manage
----

Конкретні routes залежать від теми.

Має бути:

* щонайменше один dynamic route;
* щонайменше один query-param сценарій;
* навігація без повного reload;
* зрозуміла поведінка для неіснуючого ресурсу або route.

== 4. Forms — React Hook Form + Zod

Створити щонайменше дві форми.

Перша форма повинна реалізовувати реальну предметну операцію, наприклад:

* create/edit;
* checkout;
* заявка;
* власна подія;
* запис витрати;
* заявка на усиновлення;
* додавання до playlist.

Друга форма повинна реалізовувати окремий сценарій, наприклад:

* search/filter controls;
* review/rating;
* feedback;
* comment;
* profile/preferences;
* additional domain-specific action.

Щонайменше одна форма повинна мати:

* Zod validation;
* pending state;
* success state;
* error state;
* disabled submit під час операції.

== 5. Repository та data mapping

Для основної server-side сутності реалізувати Repository.

Repository повинен приховувати від UI:

* endpoint URL;
* HTTP client;
* headers;
* DTO shape;
* низькорівневу обробку response.

Якщо це потрібно для обраного API, на рівні Repository/data-access виконати перетворення:

[source]
----
API DTO → domain model
domain input → API request DTO
----

UI не повинен залежати від випадкової форми JSON-відповіді стороннього API.

== 6. UX та async states

Асинхронний інтерфейс повинен передбачати:

* loading state;
* error state;
* retry;
* empty state;
* success feedback;
* pending state для mutation;
* disabled controls під час недоступної операції.

Для основного списку бажано використовувати окремий visual loading state, а не лише текст `Loading...`.

Для destructive action передбачити підтвердження або інший безпечний UX.
Не використовувати `alert`.

== 7. Повторне використання компонентів

Створити щонайменше два повторно використовувані UI-компоненти.

Кожен повинен реально використовуватися щонайменше у двох місцях.

Приклади:

* `Button`;
* `Card`;
* `Modal`;
* `FormField`;
* `StatusBadge`;
* `EmptyState`;
* `Pagination`.

Не створювати універсальні компоненти з десятками props лише для виконання формальної вимоги.

== 8. Тестування

Написати щонайменше **три автоматизовані тести**.

Тести повинні перевіряти не лише дрібні допоміжні функції.

Мінімально рекомендується покрити:

* одну форму або Zod-схему;
* один важливий UI-сценарій;
* одну функцію data-access / Repository або іншу критичну бізнес-логіку.

За наявності можливості використати Testing Library для перевірки поведінки UI.
