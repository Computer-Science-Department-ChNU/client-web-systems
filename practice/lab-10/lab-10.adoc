= Лабораторна робота №10

*Тема:* React та REST API: API layer, Repository Pattern, асинхронні операції та CRUD.

*Мета:* навчитися інтегрувати React-застосунок із REST API та відокремлювати UI від деталей HTTP-запитів.
Опанувати асинхронні стани, CRUD, пагінацію, скасування запитів та спрощений Repository Pattern.

== Вимоги до звіту

. Використовувати React 19.x та Node.js 22.22 або новішу версію.
. Використовувати TypeScript.
. Роботу з HTTP винести в окремий API layer.
. Реалізувати Repository для операцій над `Task`.
. Реалізувати GET, POST, PUT/PATCH та DELETE.
. Реалізувати отримання списку з пагінацією.
. Реалізувати перегляд деталей окремого `Task` через GET за `id`.
. Для асинхронних операцій передбачити loading, success, error та empty states.
. Для GET-запитів передбачити можливість скасування попереднього запиту через `AbortController` або еквівалентний механізм обраного HTTP-клієнта.
. Після помилки завантаження користувач повинен мати можливість повторити запит.
. Використати `fetch` або Axios — вибір залишається за студентом.
. API URL отримувати з environment variable, наприклад `VITE_API_URL`.
. Додати файл `.env.example` без реальних секретів.
. UI-компоненти не повинні містити URL endpoint-ів або прямі HTTP-виклики.
. Не використовувати `alert`.
. Для стилізації використати один із підходів: SCSS із дотриманням BEM, Bootstrap або Tailwind CSS.
. Якщо обрано SCSS, дотримуватися BEM-патерну для класів.
. Дотримуватися ESLint, TypeScript та Conventional Commits.

== Практична частина

=== Стилізація та BEM

Для стилізації обрати один із трьох підходів:

. **SCSS + BEM** — власні стилі з класами за схемою Block__Element--Modifier;
. **Bootstrap** — готові utility та component класи;
. **Tailwind CSS** — utility-first класи.

Не потрібно поєднувати всі три підходи одночасно.

Якщо обрано **SCSS + BEM**:

* стилі організувати за компонентами або логічними блоками;
* кожен компонент або логічний UI-блок має власний `.scss` файл поруч із відповідним компонентом;
* не зберігати стилі компонентів у загальному `App.css` або іншому великому спільному файлі;
* назви класів повинні відповідати BEM;
* не прив'язувати стилі до глибокої структури DOM;
* глобальні стилі залишати лише для справді глобальних речей: `body`, базові стилі, шрифти, reset тощо.

=== 1. Конфігурація API

Замінити локальне джерело даних Study Planner на REST API.

Для лабораторної роботи рекомендується використовувати DummyJSON з ресурсом `todos`: `https://dummyjson.com/todos`. За погодженням з викладачем можна використати інший REST API з аналогічною функціональністю.

Створити:

[source]
----
.env
.env.example
----

У `.env.example` вказати лише приклад:

[source]
----
VITE_API_URL=https://dummyjson.com
----

Файл `.env` не додавати до Git.

==== API, що використовується в роботі

Для базового варіанта використовуйте DummyJSON:

[cols="1,2,3",options="header"]
|===
|Метод |Endpoint |Призначення

|GET |`/todos?limit=10&skip=0` |список завдань з pagination;
|GET |`/todos/:id` |отримання одного завдання;
|POST |`/todos/add` |створення завдання;
|PUT/PATCH |`/todos/:id` |оновлення завдання;
|DELETE |`/todos/:id` |видалення завдання.
|===

Відповідь списку має вигляд:

[source,typescript]
----
type TodosResponse = {
  todos: ApiTodo[];
  total: number;
  skip: number;
  limit: number;
};
----

==== Важливе уточнення щодо навчального API

DummyJSON симулює POST, PUT/PATCH та DELETE: відповідь повертається, але зміни не записуються назавжди на сервері.

Після успішної mutation-операції студент повинен самостійно оновити client state/UI.
Створювати власний backend для цієї лабораторної роботи не потрібно.

Це обмеження є частиною навчального сценарію: воно дозволяє окремо продемонструвати HTTP-операцію та оновлення стану React-застосунку.

=== 2. API model та domain model

Модель, яку повертає API, не обов'язково повинна збігатися з моделлю, яку використовує UI.

Для DummyJSON todo має вигляд:

[source,typescript]
----
type ApiTodo = {
  id: number;
  todo: string;
  completed: boolean;
  userId: number;
};
----

У Study Planner можна залишити власну domain-модель `Task` з лабораторної №8.

Repository повинен виконувати mapping між API DTO та domain model, якщо це необхідно.

Наприклад:

[source,typescript]
----
function toTask(todo: ApiTodo): Task {
  return {
    id: todo.id,
    title: todo.todo,
    description: '',
    completed: todo.completed,
    priority: 'medium',
    category: 'General',
  };
}
----

Поля `description`, `priority` та `category` у такому варіанті не підтримуються DummyJSON і можуть залишатися client-only metadata.
Не потрібно вигадувати API-поля, яких немає в контракті.
Обмеження навчального API не є помилкою.

=== 3. HTTP client

Створити окремий модуль, наприклад:

[source]
----
src/
└── api/
    └── httpClient.ts
----

Він повинен:

* будувати URL із `VITE_API_URL`;
* виконувати HTTP-запити;
* перевіряти `response.ok` або еквівалентний статус;
* повертати дані або кидати помилку, яку може обробити вищий рівень.

Компоненти React не повинні знати про реалізацію HTTP-клієнта.

=== 4. Repository Pattern

Створити окремий repository для задач:

[source]
----
src/
└── repositories/
    └── taskRepository.ts
----

Repository використовується тут як навчальний приклад separation of concerns. У невеликому застосунку можна реалізувати data access простіше, але в цій лабораторній repository потрібен саме для тренування розділення UI та API-логіки.

Для DummyJSON repository повинен приховувати endpoint-и та DTO-формат.

Repository повинен надавати методи приблизно такого вигляду:

[source,typescript]
----
getAll()
getById(id)
create(task)
update(id, task)
delete(id)
----

Назви методів можна змінити, якщо вони зберігають ту саму відповідальність.

Компоненти повинні працювати з `taskRepository`, а не будувати URL endpoint-ів і не дублювати HTTP-логіку.

Не потрібно створювати складну універсальну систему repository для всього застосунку.
Достатньо одного зрозумілого repository для `Task`.

=== 5. Завантаження списку та пагінація

При відкритті Study Planner:

. показати loading state;
. викликати `taskRepository.getAll()`;
. відобразити отримані задачі;
. у разі помилки показати зрозуміле повідомлення;
. дати користувачу можливість повторити запит;
. дозволити перейти на наступну та попередню сторінку;
. показувати номер поточної сторінки або інший зрозумілий індикатор позиції.

Для DummyJSON можна використовувати `limit` і `skip`.

Під час переходу між сторінками попередній GET-запит потрібно скасувати, якщо він ще виконується.

=== 6. Loading, error, empty та success

Реалізувати окремі візуальні стани:

[source]
----
Loading...
Помилка завантаження. [Спробувати ще]
Завдань не знайдено.
----

Порожній результат не повинен виглядати як зламаний інтерфейс.

=== 7. Деталі завдання

При виборі завдання відкрити його деталі та отримати актуальні дані через `taskRepository.getById(id)`.

У деталях показати щонайменше назву, опис, категорію, priority та completed.

Дані для деталей не потрібно дублювати в окремому глобальному Context: достатньо локального state компонента або іншого простого client-side state.

=== 8. Створення завдання

Форма з лабораторної №8 повинна створювати нове завдання через `taskRepository.create()`.

Після успішного створення:

. оновити список у UI;
. очистити форму;
. показати короткий success state або inline-повідомлення.

=== 9. Оновлення та видалення

Для існуючого завдання реалізувати:

* перемикання `completed`;
* редагування назви;
* видалення.

Операції повинні проходити через repository.

Для видалення додати зрозуміле підтвердження в інтерфейсі.

=== 10. Скасування запитів

Для списку та деталей використовувати асинхронний запит із можливістю скасування.

Приклад для `fetch`:

[source,typescript]
----
const controller = new AbortController();

fetch(url, { signal: controller.signal });

return () => controller.abort();
----

Якщо використовується Axios, скористайтеся його підтримкою `AbortSignal`.
Скасований запит не повинен показуватися користувачу як звичайна помилка завантаження.

=== 11. Архітектура стану

Розділити:

* **server state** — дані, отримані через API;
* **client/UI state** — фільтр, поточна сторінка, стан форми, selected task тощо.

Поточний localStorage із лабораторної №9 не потрібно використовувати як друге джерело правди для server state.
Якщо потрібне локальне збереження, його можна залишити лише для client/UI state.

=== 12. Збереження коду з лабораторної №9

Context, reducer та Custom Hooks із попередньої лабораторної можна зберегти там, де вони справді корисні.
Не потрібно переносити server state у `TaskContext` лише для того, щоб зберегти архітектуру №9.
Дані `Task`, які приходять із server state, не повинні дублюватися без потреби в кількох незалежних state.

=== 13. Додаткові завдання

. Додати пошук із debounce.
. Реалізувати optimistic update для зміни `completed`.
. Додати Axios instance з базовим URL.
. Додати централізовану нормалізацію помилок.

== Демонстрація на захисті

За час захисту необхідно продемонструвати:

. завантаження списку із REST API та пагінацію;
. відкриття деталей окремого завдання;
. створення нового завдання;
. одну операцію оновлення або видалення;
. loading/error/empty/success state;
. у коді показати `httpClient`, `taskRepository` та скасування GET-запиту.


Не потрібно демонструвати всі додаткові можливості.
