= Лабораторна робота №7

*Тема:* Підсумковий проєкт: Vue 3, TypeScript, API, Pinia та архітектура Feature-Sliced Design.

*Мета:* спроєктувати та реалізувати завершений SPA-застосунок на Vue.js, використовуючи підходи та інструменти, вивчені у роботах №1–6.

Це *фінальний проєкт блоку Vue.js*.
Проєкт виконується командою, яка сама визначає структуру застосунку, склад сторінок, спосіб взаємодії його частин та конкретні деталі реалізації.

Важливо показати не окремі приклади технологій, а завершений продукт із логічною архітектурою та цілісним користувацьким сценарієм.

== Командна робота

Проєкт виконується командою з *3 студентів* (у виняткових випадках - 4).

Один з учасників (тимлід) створює для проєкту *окремий GitHub-репозиторій* і додає решту учасників як collaborators.
Викладач повинен мати доступ до репозиторію.

=== Git flow

Команда працює за моделлю *GitHub Flow*:

* `main` - стабільна гілка, з якої виконується deployment; прямий push у `main` заборонено (branch protection rule);
* кожна задача виконується в окремій короткоживучій гілці, створеній від `main`:
** `feature/<коротка-назва>` - новий функціонал (наприклад, `feature/search-shows`);
** `fix/<коротка-назва>` - виправлення помилок;
** `chore/<коротка-назва>` - налаштування, залежності, CI;
* зміни потрапляють у `main` лише через *Pull Request*;
* кожен PR повинен мати щонайменше *один approve від іншого учасника* команди;
* перед merge PR повинен проходити CI (GitHub Actions): ESLint, `vue-tsc --noEmit`, build;
* конфлікти розв’язує автор PR (rebase або merge `main` у свою гілку);

Коміти оформлюються за https://www.conventionalcommits.org/[Conventional Commits] (`feat:`, `fix:`, `refactor:`, `chore:`, `docs:`).
Squash merge не використовуйте, щоб історія комітів кожного учасника залишалась видимою.

=== Порядок старту

. Тимлід створює каркас проєкту (Vite, TypeScript, ESLint, Husky, структура шарів FSD, `shared/api`, router, CI) та додає його в `main`.
. Команда декомпозує проєкт на задачі (GitHub Issues) і веде їх на дошці GitHub Projects.
. Задачі розподіляються за слайсами FSD, щоб учасники якомога менше змінювали ті самі файли.
. Кожен PR посилається на свою задачу (`Closes #N`).

== Архітектура

Проєкт організовується за *Feature-Sliced Design (FSD)*, як у роботі №6.

Використовуйте шари в такому порядку (зверху вниз):

* `app` - ініціалізація застосунку, router, підключення Pinia, глобальні стилі та провайдери;
* `pages` - сторінки, прив’язані до маршрутів;
* `widgets` - великі самостійні блоки сторінок;
* `features` - дії користувача, що мають бізнес-цінність (пошук, фільтр, додати в обране, форма створення тощо);
* `entities` - предметні сутності: типи, модель, UI-представлення, доступ до даних;
* `shared` - повторно використовуваний код без прив’язки до предметної області (HTTP-клієнт, UI-kit, утиліти, конфігурація).

Шар `processes` не використовується.

Обов’язкові правила:

* модуль може імпортувати лише з *нижчих* шарів;
* слайси одного шару не імпортують один одного напряму;
* кожен слайс має публічний API (`index.ts`), зовнішній код імпортує лише через нього;
* `shared` не знає нічого про предметну область.

Приклад структури (орієнтир, не шаблон для копіювання):

[source]
----
src/
├── app/
│   ├── router/
│   ├── providers/
│   ├── styles/
│   └── main.ts
├── pages/
│   ├── catalog/
│   ├── item-details/
│   ├── favorites/
│   └── not-found/
├── widgets/
│   ├── header/
│   └── item-list/
├── features/
│   ├── search-items/
│   ├── sort-items/
│   └── toggle-favorite/
├── entities/
│   └── item/
│       ├── api/        # repository
│       ├── model/      # типи, store, composables
│       ├── ui/         # ItemCard.vue тощо
│       └── index.ts    # публічний API слайсу
└── shared/
    ├── api/            # HTTP-клієнт, базові налаштування
    ├── ui/             # власні базові компоненти
    ├── lib/            # утиліти, загальні composables
    └── config/
----

Незалежно від конкретної структури повинні бути зрозумілими:

* відповідальність кожного слайсу;
* межа між UI та data-access;
* напрямок залежностей;
* місце зберігання server state та client/UI state.

Для роботи із server-side даними *Repository є обов’язковим*.

== Server state та client state

Розрізняйте два види стану:

* *server state* - дані, власником яких є сервер (список товарів, деталі серіалу, автори тощо).
Отримуються через Repository, а стан запиту (`loading`, `error`, `data`) інкапсулюється у composable (`useItems`, `useItemDetails`) або в Pinia-store відповідної сутності;
* *client/UI state* - дані, власником яких є сам застосунок (обране, власний список, налаштування, вибрана тема, чернетка форми).
Зберігаються у *Pinia*.

Не копіюйте server state у кілька місць без потреби.
Один ресурс - одне джерело правди.

Pinia-store пишіть у стилі *setup store* (`defineStore('id', () => { ... })`) із типізованим станом.

== API та Repository

Застосунок повинен працювати із зовнішнім API або іншим зовнішнім джерелом server state.

HTTP-клієнт (`fetch` або `axios`) налаштовується один раз у `shared/api`.

Repository розміщується в шарі `entities` (наприклад, `entities/item/api/itemRepository.ts`) і повинен відокремлювати UI від деталей API та HTTP-взаємодії.
Компоненти та сторінки *не* викликають `fetch`/`axios` напряму.

Для основної предметної сутності передбачте операції, необхідні для реалізованого сценарію.

Якщо формат API-відповіді не збігається з моделлю, яку використовує UI, ізолюйте це на data-access рівні (DTO → модель через mapper-функції).
Типи DTO не повинні «протікати» у компоненти.

=== Примітки до тем

* *Mini Shop*, *Recipe Planner* - DummyJSON підтримує пагінацію (`limit`, `skip`), пошук (`/search?q=`) та сортування (`sortBy`, `order`) на сервері.
Mutation-запити (`POST`/`PUT`/`DELETE`) повертають результат, але на сервері не зберігаються.
* *TV Show Explorer* - список серіалів (`/shows?page=N`) має серверну пагінацію, але не має сортування та фільтрів; пошук (`/search/shows?q=`) не має пагінації.
Сортування та фільтрацію за жанром реалізуйте на клієнті.
Акторів отримуйте через `/shows/:id/cast`.
* *Book Tracker* - для пошуку використовуйте https://openlibrary.org/dev/docs/api/search[Search API] (`page`, `limit`, `sort`), для авторів - https://openlibrary.org/dev/docs/api/authors[Authors API], для обкладинок - https://openlibrary.org/dev/docs/api/covers[Covers API].
* *Pet Adoption* - server-side каталог - це породи; пагінація серверна (`page[number]`, `page[size]`).
Пошуку за назвою в API немає - реалізуйте його на клієнті; фільтр за групою - через `/groups`, де кожна група містить список своїх порід.
API не містить зображень, вони не обов’язкові.
Тварин для усиновлення та заявки реалізуйте як client-owned сутності (CRUD у Pinia з persistence).

=== Загальне правило

Якщо API не підтримує серверну пагінацію, сортування або фільтрацію, реалізуйте їх на клієнті - у composable або моделі сутності, із синхронізацією з `route.query`.

== Обов’язковий функціонал

Готовий проєкт повинен містити:

. щонайменше *дві пов’язані server-side сутності або ресурси*;
. список основної сутності та сторінку її детального перегляду;
. щонайменше *чотири змістовні маршрути* та сторінку 404;
. dynamic route (`/items/:id`) та query-param сценарій: стан пошуку/фільтрів/сортування сторінки синхронізується з `route.query`, тож посиланням можна поділитися, а кнопки «Назад/Вперед» браузера працюють коректно;
. пошук або фільтрацію (для пошуку - debounce, реалізований через `watch` або власний composable);
. сортування;
. pagination або infinite scroll (якщо воно доцільне і підходить до проєкту);
. щонайменше одну значущу CRUD/mutation-операцію;
. щонайменше *дві форми* з `v-model`, одна з яких виконує реальну предметну операцію;
. валідацію форм із виведенням повідомлень про помилки біля відповідних полів і блокуванням відправки некоректних даних;
. окремий client/UI state у *Pinia*;
. persistence для client-owned state (`localStorage` - власний Pinia plugin або `pinia-plugin-persistedstate`);
. Repository для роботи із server-side даними;
. щонайменше *чотири повторно використовувані UI-компоненти* з типізованими props і emits; хоча б один із них використовує slots;
. щонайменше *два власних composable* (`useXxx`), що інкапсулює логіку, а не лише обгортає один виклик;
. змістовне використання `computed` та `watch`;
. loading, error, empty та success states;
. pending state під час mutation (блокування кнопки, індикатор);
. можливість повторити невдалу асинхронну операцію (кнопка «Спробувати ще раз»).

Якщо обране API не підтримує потрібну mutation, дозволено реалізувати CRUD для власної client-owned сутності (наприклад, watchlist, план харчування, нотатки до книги, заявки на усиновлення).
Основний server state при цьому все одно повинен проходити через Repository.
